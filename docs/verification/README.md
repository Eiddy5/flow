# 工作流验证文档

本目录用于保存工作流核心的场景验证文档。每个可独立执行和判断结果的验证场景使用一个 Markdown 文件，不把多个无关场景合并到同一个文件中。

## 文件命名

文件名使用两位数字序号和简短英文场景名：

```text
01-flow-start-and-node-progression.md
02-manual-task-completion-and-permission.md
03-conditional-flow.md
04-parallel-flow.md
05-cyclic-flow.md
06-flow-version-binding.md
```

序号表示 MVP 验证顺序，不表示实现类或测试类的名称。

## 文档结构

每个验证文档应包含以下内容：

```markdown
# 验证名称

## 验证标识

## 前置条件

## 验证场景

## 验证方式

## 通过规范

## 反例
```

## 编写规则

- 一个文档只验证一个主要运行场景。
- “验证场景”用于列举该验收主题下的各种具体情况，每种情况使用唯一的场景编号。
- 同一个验收主题存在不同节点组合、输入或运行结果时，必须拆成多个具体场景。
- “验证方式”必须按照场景编号逐一描述准备数据、调用步骤、查询动作和需要观察的状态。
- “通过规范”必须按照场景编号逐一列出；一个场景存在多个要求时，每条要求都必须独立编号。
- Flow 定义必须写明 Node、Edge、条件和关键 config。
- 验证方式必须写明调用的方法、输入参数和调用顺序。
- 通过规范分别检查 Process、Executor、Activity 和 Task。
- 涉及版本时必须断言 Process 绑定的 `flowId` 和 `flowVersion`。
- 涉及人工节点时必须分别验证 complete 前和 complete 后的状态。
- 涉及条件、并行或循环时必须写出实际经过的 Node 路径。
- 通过规范必须是可观测、可重复判断的结果，不能只写“流程运行正常”。
- “反例”只记录验证过程中真实出现的问题，不预先罗列假设问题，也不能编造验证结果。
- 每条反例必须记录对应场景、操作步骤、实际结果、预期结果、影响、处理结论和复验结果。
- 尚未执行验证或验证时没有发现反例，应明确记录“本轮暂无反例”。
- 当前第一阶段使用内存 Session、Transaction 和 Query Adapter，验证文档不得依赖数据库。
- 每个验证文档最终应对应至少一个自动化测试类。

## MVP 验证顺序

1. 流程启动与自动、人工节点推进。
2. 人工 Task 的 complete、权限和幂等。
3. 条件路由。
4. 并行分叉与汇合。
5. 循环流程和自动循环保护。
6. Flow 发布、版本升级和 Process 版本绑定。
7. 多 Process 实例隔离。
8. 重复 complete 和运行幂等。
