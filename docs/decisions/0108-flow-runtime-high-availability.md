# ADR 0108：Flow 运行逻辑闭环与稳定性

## 状态与范围

Proposed，2026-09-22。用户最新澄清：“高可用”指**逻辑全面闭环、运行非常稳定**。
进一步明确验证对象是原生 Task、编排机制和触发器，而非审批等业务流程。
分支、串行、并行、循环、子流程、定时和触发的状态正确性，以及应用进程崩溃后
恢复推进，是本轮验证目标。既有审批命名仅是历史测试样例，不表示 Flow 提供审批能力。
本方案据此调整，不再以跨可用区拓扑、集群切主和 RTO/RPO 为主要目标。
先前跨可用区建议不作为当前已接受的架构决策或实施任务。

本文初稿只形成运行语义梳理与完善顺序，没有修改生产实现、Schema 或 UC。
后续压力验证的环境与复跑约定见 [运行逻辑压力验证](../harness/flow-runtime-stress.md)，
执行结论以对应测试报告为准，不能将本方案视作验证通过的证据。
文中建议的行为尚未全部确认；已有 Accepted ADR 和 UC 仍是现有业务预期来源。

目标是在框架已承诺的能力范围内，每个输入、状态、操作、异常和允许的能力组合都有
明确结果：能够继续推进、进入有原因且有恢复入口的合法等待、按策略重试，或到达
一致的终态。等待人工处理的 Pause 可以长期等待，不能仅因持续时间长就判定为卡死。

全面闭环不要求一次实现所有新功能。不支持的组合应在发布或操作入口明确拒绝，
不能允许配置成功却在运行中无效果，或让运行永久停在无法解释的状态。

## 背景与现状

Flow 已具备定义版本、顺序/条件/并行/循环、Pause、退回派生、SubFlow、四类触发器、
RunnableTask 重试、运行持久化与 CAS。它们构成运行主干，但单项存在不等于组合行为
和异常收尾已经完整。

以下是当前工作区的源码和已有文档证据，不是本轮新执行的测试结果：

| 检查项 | 当前事实 | 本轮应如何理解 |
| --- | --- | --- |
| 状态迁移 | State.withState 追加历史；StateTest 仍要求拒绝若干迁移。已有报告记录该分歧 | 先明确 State 值对象和 Execution/TaskRun 领域行为分别负责哪些约束，不能直接判定哪一方正确 |
| Pause 超时 | duration/behavior 有定义与校验，运行时未接通超时推进 | 已暴露配置尚无完整行为，需要落地或明确限制其可用性 |
| Parallel 并发 | 有分支编排；concurrent 没有执行侧调用点，Worker 在处理器内逐个调用 | 编排语义与真实执行行为需要对齐，不能把配置字段等同于能力完成 |
| SubFlow | 首次调用、基本失败和结果返回已有实现 | ADR 0098 明确未实现子取消传播、Replay 接续和跨保存/发消息的中断恢复 |
| 重试 | 三种策略、预算、等待恢复和取消已有实现 | 仅 RunnableTask 可配置；等待重试恢复不等于执行中失联恢复；重复/迟到结果的真实注入验收仍有缺口 |
| Worker 失败 | 明确返回/抛出的业务失败有处理路径 | RUNNING 保存后中断、外部操作完成而结果未保存，仍需要可解释的恢复路径 |
| 子流程交接 | 父子状态保存与后续 emit 分开 | 重投可能遇到已改变的状态并跳过原分支，需要验证并补足必要的后续推进 |
| 验证 | 最近回归报告记录 528 项调用、527 通过、1 项 StateTest 失败 | 部分测试通过不能代替完整语义与组合验收；build/AOT 未完成事项单独保留 |

### 2026-09-22 本地隔离验证补记

本轮真实执行结果见 [批量报告](../test-reports/flow/BATCH-2026-09-22-1641.md) 和
[压力报告](../test-reports/flow/STRESS-2026-09-22-1641.md)。全程使用专属本机
PostgreSQL/Pulsar，没有使用生产环境；归档后已清理这两个临时容器。

- 105 个已确认 UC 场景最终为 103 PASS、1 FAIL、1 NOT_COVERED。
  UC02 S7 的恢复与取消竞争发现反例：根运行与 Pause 均为 KILLED，Pause 仍保留
  已提交的 decision 输出；独立定向复验 11 个旅程中出现 2 次，未修改原有断言。
- 明确排除该竞争场景后，其余八类场景在本地正式连接池实现下完成
  1/4/16/32 并发阶梯共 1024 个旅程，以及 16 并发持续 600 秒的 9099 个旅程，
  均完成逐实例断言。它们证明已测范围的收敛，不代表全组合通过或生产容量认证。
- 完整回归汇总 529 项结果为 527 通过、1 失败、1 默认关闭的长压测入口跳过；
  其中 Scheduler/Server 的 48 项来自刚完成模块回归的缓存。StateTest 的既有分歧
  仍可独立复现；UC18 S9 的重复/迟到 WorkerTaskResult 真实注入仍未覆盖。
- 清理前 12911 个实例均为终态，但仍有 1 条关闭夹具后未发布的 FLOW_TERMINATED
  事件，记录 QueueException；本轮没有重启验证该事件恢复。未参与本轮 Core 持续
  压力消费的调度配置订阅也保留积压，不能据实例终态宣称所有消息交接已闭环。

因此，本 ADR 保持 Proposed，逻辑全面闭环尚未达到。当前优先项是已有 UC 的竞争
反例、状态迁移契约分歧，以及结果重投和关闭恢复边界的验证；本轮没有修改生产实现。

### 2026-09-22 原生机制崩溃验证补记

新增已确认 [UC-19](../uc/flow/UC-19%20原生流程运行崩溃恢复.md)，以实际应用 JVM
异常退出后原实例能否继续为验收条件。验证方法见
[原生机制恢复手册](../harness/flow-native-recovery.md)，逐场景证据见
[UC-19 报告](../test-reports/flow/UC-19-2026-09-22-2035.md)。同定义的 9 个无崩溃对照
全部通过，但崩溃矩阵的 12 个场景中仅 4 个通过、8 个失败；参数展开为 14 项，
5 项通过、9 项失败。这个结果不能支持“底层框架已稳定，剩下只需扩展 Task”。

共同反例是 RunnableTask 的 RUNNING 已持久化、外部调用尚未完成时进程被强杀。
新 JVM 启动后，在 35 秒观测窗口内原任务和根运行仍为 RUNNING；对应消息订阅
积压及未确认数量为 0，未观察到新的该任务调用。串行、分支、并行、循环以及
四类触发启动的运行均能复现。它们属于同一恢复缺口的多个上下文，不能计作
八个相互独立的根因，也不能把有限时间观测表述为无限期卡死的证明。

源码链路与该结果一致：执行器先保存 RUNNING 再同步调用 Worker，重新规划只派发
CREATED 任务；原 RUNNING 任务没有在这条重投路径获得接续。消息处理正常返回后
可以被确认，因而“消息已消费”不能证明运行已恢复。补齐机制时需要判断原执行者
是否仍有效及外部操作结果是否确定，不能简单把所有 RUNNING 重置成 CREATED。

通过的窗口是子流程暂停后恢复、子流程终态已保存但尚未合并至父流程、等待重试，
以及终态保持。子流程结果交接的其他保存/发布窗口未因此获得通过结论。历史
恢复与取消竞争、State 契约分歧和重复/迟到结果注入缺口仍未关闭。本轮仅新增
验证能力，没有修改生产运行机制或 Schema。

后续全项目回归还观察到关闭阶段阻塞：`TriggerRuntime.publishPending` 持锁等待
Pulsar producer 创建，`TriggerRuntime.shutdown` 等待同一锁。间隔线程栈保存了
该现象，Core 回归因此未正常完成。这是独立于 UC-19 恢复反例的生命周期观察；
独立方法复验通过，未执行的 53 个 Core 测试类补跑 263 项全部通过，但首次全量
运行并未因此变成无中断通过。Scheduler 在全量跨模块运行时另有 ACK 失败，
在共用 Broker 上单独复现；日志显示之前 Core 测试插件类型无法反序列化，提示
测试消息隔离问题。精确边界及最终统计见报告，不据局部通过宣称完整构建已通过。

## 备选方案

1. 继续扩展 Task 类型，并在具体业务中逐个补漏洞：短期能增加场景，但容易把相同
   生命周期问题重复写进插件，组合时出现不同结果。
2. 先确定现有框架的运行不变量和操作矩阵，逐条核对实现、补齐缺口、验证组合，再扩展
   插件：建议采用，优先保证已有能力的语义一致。
3. 先建设跨 AZ 部署与复杂调度基础设施：不能直接解决父子取消、结果传播和退回等
   逻辑缺口，不作为本次主线。

## 建议决策：以运行闭环组织检查

### 1. 生命周期与终态

分别梳理 Execution、TaskRun、业务 Attempt 的创建、运行、等待、完成、失败和取消。
不能直接把同一套状态转换表不加区分地套在不同对象上。

每个公开操作要明确：允许的前置状态、身份范围、状态变化、输出、失败原因、重复
操作结果，以及如何查询最终结果。受理成功与执行完成必须区分。

应满足的方向性不变量：

- 成功或警告结束时，不能遗留本实例应完成而未完成的节点。
- 失败/取消后，尚未启动的工作不再启动，等待重试不再产生新调用。
- 终态后的旧消息和旧结果不能使同一个实例重新运行。
- 无可运行节点时，必须能说明是在合法等待、已经收敛，还是出现了应报告的异常。
- 逻辑取消与物理调用停止分别表达，不能把 TaskRun 标记 KILLED 当成外部副作用已撤回。

StateTest 的分歧先按已确认语义解决，不能仅为了绿色结果删除断言或任意增加全局限制。

### 2. 编排与结果传播

逐个检查顺序、条件、并行和循环在正常、空集合、跳过、警告、失败及嵌套情况下的结果。

- 顺序：前置步骤未完成不执行下游；失败后不泄漏后续调用。
- 条件：命中与未命中的路径可解释；未选中输出不可冒充已产生结果。
- 并行：每个分支独立推进，汇聚只发生一次；分支失败后其余分支的逻辑收尾和
  已在途调用如何处理，需要一致的契约。
- 循环：轮次、退出条件、最大轮数和跨轮输出作用域一致；恢复后不能重复或跳过一轮。
- 数据：必填、默认值、缺失/null、输出类型错误及引用不可见结果，均有确定处理路径。
- 输出校验异常需要核对能否得到明确失败结果，不能仅抛给消息层而留下无恢复入口的 RUNNING。

对象/数组输入、通用表达式映射等是可选能力扩展；现有范围内先保证结果正确和
不支持的用法明确被拒绝。

### 3. Pause、重试与等待

必须区分等待人工输入、等待重试时间、等待子流程与任务执行中，避免混用一种恢复策略。

- Pause 前置任务只按定义执行；恢复参数非法时原等待事实保持一致。
- 相同 Resume 的重复提交、不同结果同时提交、恢复后下游失败，均有明确结果。
- 已配置超时的 Pause 需要真正的到期处理；超时与人工恢复竞争只产生一次有效推进。
- 业务重试与消息重投、CAS 保存重试分别计数，不能把基础设施重试变成额外业务调用。
- 重试耗尽要明确失败，成功保留历史，取消后迟到唤醒不再调用业务。
- Retry 总预算不等于单次执行超时；阻塞调用需要独立处理规则。

未配置自动截止的合法人工等待可以继续存在，其状态、原因和可操作入口必须可查询。

### 4. 取消、退回和子流程

这部分是现有能力组合的优先检查项，不能由几个正常案例推定全部完成。

| 组合 | 需要确定并验证的语义 |
| --- | --- |
| 并行中一支失败、一支暂停或重试 | 根如何结束，其他节点和延迟计划如何关闭，是否还有后续业务调用 |
| Pause 恢复与取消同时发生 | 哪个操作生效，另一个返回什么，是否可能重复推进 |
| 退回后的旧实例收到恢复/Worker 结果 | 原实例保持停止，结果不能进入派生实例 |
| 嵌套并行/循环退回 | 影响范围准确，未受影响分支保留，轮次与输出不串用 |
| 父流程取消、失败或退回时子流程仍运行 | 子流程取消、保留或重新关联的规则必须明确，不能留下无归属工作 |
| 子流程成功、失败或被单独取消 | 父调用节点和父运行如何收敛，结果如何保留 |
| 子流程完成通知重复或交接中断 | 父流程不重复推进，也不会因遗漏通知永久等待 |

当前 SubFlow 取消传播和 Replay 接续尚不属于已完成范围。需要先确认预期，再形成
对应 UC 和实现；本文不擅自决定父取消必然级联所有子运行等业务规则。

### 5. 异常、中断与重复操作

运行逻辑闭环包含同一进程重启和消息异常，不必先引入跨 AZ 架构才能检查。

检查 Create、Resume、Cancel、Rewind、Worker 结果与子流程交接的每个“保存—发布”
交界点：重复投递是否安全，中断后是否有事实可恢复，旧事件是否可能覆盖新事实。

区分三类失败：

- 确定的业务失败：按已定义的重试或失败收敛。
- 存储/消息暂时失败：保留待完成动作，恢复后重做交接，不能随意重跑已完成业务。
- 外部结果不确定：先按稳定幂等键或业务编号核实；无法核实时显式报告，不能猜测成功
  或盲目再次调用。

优先复用现有 CAS、稳定身份与 Outbox，只在具体缺口需要时补足恢复协议。
不把上一版方案的独立 Worker 集群、租约体系和全部新增持久化结构直接当成已接受方案。

### 6. 查询、反馈与历史

查询应能解释当前状态及原因：等待谁、等待什么、下一次重试时间、最新失败原因、
当前轮次、父子关系和退回来源。

异步操作返回受理时，调用方应知道如何查询最终生效结果。历史版本与实际运行保持
对应；不存在、已删除、跨租户或已失效的目标应得到一致的错误，不进入无限消息重投。

技术修复和人工干预需要可追踪，不能直接修改数据库状态制造表面终态。

## 实施顺序

| 阶段 | 工作 | 完成边界 |
| --- | --- | --- |
| 1. 运行契约 | 以当前 Accepted ADR/UC 为依据整理对象状态、操作和组合矩阵；标明未定义事项 | 每条支持路径有前置条件、状态结果、输出、失败和重复语义；未确认规则明确列出 |
| 2. 已有缺口 | 优先处理状态约束分歧、Pause 超时、Parallel 执行语义、父子流程收尾和中断交接 | 实现兑现当前声明；暂不支持的能力有明确限制；不扩大插件功能范围 |
| 3. 验证闭环 | 按已确认用户场景验证正常/失败/取消/恢复；以技术测试验证竞争、重复、乱序和中断 | 完整用例链条有证据，缺口不被技术测试数量或参数分支掩盖 |
| 4. 稳定回归 | 嵌套组合、持续反复运行、受控并发和长时间等待恢复；完整构建 | 无无法解释的活动实例、重复下游或状态/历史不一致，所有剩余问题有明确结论 |

UC 创建或覆盖审计由 UC Agent 负责，测试与报告由 Test Agent 负责，二者按仓库规则
顺序协作。必须先确认新增业务预期，不能从当前代码或技术架构反推 UC。
初稿阶段没有开始 UC 覆盖审计或测试执行。后续执行证据见本文的本地验证补记和
对应报告；不能据已测场景给本节所有检查项赋予 PASS。

## 稳定性的验收标准

1. 已支持能力没有“配置可接受，但运行无效果”的隐含入口。
2. 每个非终态实例都有可解释的推进条件或合法等待原因。
3. 每个正常、失败、取消和恢复路径都完成用户可查询的收尾。
4. 重复、乱序和迟到结果不改变已经确定的有效事实，也不重复执行下游。
5. 嵌套与组合遵循相同规则，不靠插件或调用方绕过框架状态机。
6. 中断后可按持久化事实继续或明确失败；不确定外部结果有处理出口。
7. 已确认 UC、技术回归及完整构建通过；未验证内容如实标记，持续运行结果可复查。

## 理由与后果

先补齐现有运行语义，能把生命周期规则集中在框架，避免后续每个 Task 重复处理取消、
重试、回调和恢复。代价是新增业务插件暂不作为主要产出，需要先解决已有规则分歧和
未定义组合。本方案不会仅因为缺少一项高级特性就判定框架不稳定；稳定性评价只针对
明确声明支持的范围和对应证据。
