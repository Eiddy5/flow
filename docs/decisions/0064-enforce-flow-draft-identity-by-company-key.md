# ADR 0064：按 company_id 和 key 唯一确定 FlowDraft

## 状态

Accepted

领域方法的命名已由 ADR 0067 修订：`FlowDraft.id()` 返回稳定字符串实体 ID，
`flowKey()` 返回业务 key；本 ADR 的唯一性与查询选择器保持不变。

## 背景

FlowDraft 同时拥有数据库行标记 `id` 和 Flow 业务 `key`。历史调用路径曾把 `id`
作为草稿、部署和查询入口，导致同一个业务 Flow 可能被重复创建，也让技术存储标识
泄漏到业务协议中。

## 决策

- FlowDraft 的业务身份是 `(company_id, flow_key)`；`id` 只作为数据库行标记和持久化
  适配器内部的精确行定位字段。
- `flow_key` 在创建草稿时必须由调用方提供，并在草稿生命周期内保持不变。
- `flow_drafts` 使用全量唯一约束 `UNIQUE (company_id, flow_key)`。软删除是终态，
  不会释放同一公司下的 key。
- 保存草稿是一个按 `(company_id, flow_key)` 执行的 upsert：先在当前事务中锁定并查询
  业务 key，存在则修订原草稿，不存在则创建新草稿。
- 草稿的 HTTP、Service、Command、Query 和部署/删除流程统一按 `companyId + key`
  选择；按 `id` 的 Repository 方法仅保留给适配器内部和已有技术行恢复场景。
- 修订内容可以不包含 YAML 顶层 `key`；如果包含，必须与草稿 key 一致，不能通过
  保存或部署改名。

## 理由

数据库唯一约束是并发创建时的最终一致性边界，应用层的按 key 查询和行锁则负责
更新、部署、删除时的租户隔离与乐观锁。把软删除行也纳入约束，保证“同一公司同一
key 只能有一个”在整个生命周期内成立，避免历史版本和新草稿产生歧义。

## 后果

- 保存草稿接口需要独立传入业务 key；原始 YAML 可以继续作为不透明内容保存。
- 同公司重复 key 返回业务冲突；不同公司可以使用相同 key。
- 软删除后若要重新使用相同 key，需要另行定义恢复或归档策略；当前实现不自动释放。
- 开发期 PostgreSQL 基线和 JOOQ 元数据必须同步重建，不能依赖旧表结构自动升级。
