# ADR 0125：由构建选择 Java 版本

## 状态

Accepted（2026-10-14）。用户确认最低支持 Java 21，取消项目固定的 Java 版本，
由引入项目时的构建环境选择。本决策修订此前 Java 25 的构建要求；模块、依赖版本
和运行协议不变。

## 背景

Flow 已成为可直接引用的 Java Library，但根构建将编译、测试和工具执行固定为
Java 25。这会覆盖宿主选择，并使另一 JDK 上的源码消费也需要准备 Java 25。
当前源码中的未命名 lambda 参数和资源变量可改为等价的具名变量，避免仅为该
语法要求 Java 22；Java 22 的 `InetAddress.ofLiteral` 也需要等价替换，保持仅解析
地址字面量、不进行 DNS 查询的安全语义。虚拟线程、集合 API 和现有依赖仍具有
Java 21 的实际能力要求。

Java 版本有三个不同边界：源码构建时使用的编译器、工具与测试运行时使用的 JDK，
以及已编译制品的目标字节码。取消构建中的固定值只改变版本选择权，不能让既有
JAR 自动适配更低版本的虚拟机。

## 备选方案

1. 继续固定 Java 25：不能满足宿主统一选择的需求，不采用。
2. 改为固定 Java 21 或新增 Flow 专属版本属性：仍维护另一套版本选择规则，不采用。
3. 采用 Gradle 标准 Java 配置和默认 JDK，并保留真实目标元数据：采用。

## 决策

- 移除根构建中固定为 25 的编译和测试 toolchain 配置；不增加固定的
  `sourceCompatibility`、`targetCompatibility` 或 `options.release`。
- 编译和测试遵循所属项目的标准 `java.toolchain`；没有显式设置时，使用 Gradle
  默认选择，即运行 Gradle 的 JDK。宿主可在同一多模块构建中统一配置各项目。
- Schema 导出等 `JavaExec` 任务通过
  `javaToolchains.launcherFor(project.java.toolchain)` 使用所属项目的 toolchain，
  避免工具运行 JDK 与源码构建配置分离。
- 移除不再参与当前产品构建的自运行脚本模板中的 Java 25 检查，以及只能用于更高
  JDK 的固定启动参数，避免未来复用模板时重新施加不一致的版本要求。
- 将未命名 lambda 参数和资源变量改为具名变量；以兼容 Java 21 的地址字面量解析
  替换 `InetAddress.ofLiteral`，保留无 DNS 查询及原有安全语义，不升级或降级依赖。
- 保留 Gradle 根据实际编译配置生成的 Java 目标版本属性和发布元数据，不隐藏或
  伪造字节码的兼容性要求。

## 理由

统一使用 Gradle 的既有选择机制，使宿主与开发环境可以决定编译和执行 JDK，
不需要维护 Flow 专用的版本参数。工具与测试跟随项目配置，避免编译后由另一版本
的 Java 执行。实际兼容性通过源码、依赖、元数据及运行验证共同保证。

## 后果与验证

最低支持 Java 21，与当前源码和依赖的实际能力要求一致；不在构建中新增固定
toolchain。未来引入更高版本的语言特性或依赖时，需要先修订最低支持版本的决策，
并验证兼容性变化。

`includeBuild` 仍是独立构建，调用工程的 `java.toolchain` 不自动继承到 Flow。
两个构建都未配置 toolchain 时，由各自 Gradle JVM 决定，通常共用启动构建的环境；
显式选择不同 JDK 时，调用方需同时配置两个构建。已发布制品在构建时确定字节码，
消费方 JDK 不会改变它；发布构建必须面向预期运行环境选择 JDK。

验证应检查默认 JDK 下的全模块编译和测试编译、Schema 导出、运行依赖隔离、
独立 Java 消费、真实 PostgreSQL 装配及完整模块回归，并核对实际编译器、测试和
工具 launcher。原 Java 25 的测试记录保留为历史证据，不代表本次 JDK 验证通过。
使用说明见 [Java 使用指南](../harness/java-engine.md#java-版本选择)。
