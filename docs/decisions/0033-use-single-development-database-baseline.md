# ADR 0033：开发期使用单一数据库建表基线

## 状态

Accepted（基线改由人工执行、Flow Server 不再使用 Flyway 的条款由
[`ADR 0039`](0039-embed-complete-flow-server-in-cses.md) 修订；单一物理文件布局由
[`ADR 0048`](0048-isolate-schema-ddl-and-pluralize-table-names.md) 修订）

## 背景

Flow 尚处于开发阶段，当前 PostgreSQL 中没有需要跨版本保留的生产数据。仓库此前
按日期累积了建表、改名、回填、状态收敛和约束调整等 11 份迁移脚本；空数据库必须
执行完整历史链才能得到当前 Schema，阅读和修改成本已经高于这些开发期兼容逻辑的
价值。

当前开发方式允许数据库结构变化破坏已有开发数据。此时继续维护旧列、旧状态、旧
类型地址和数据回填路径，会让已经废弃的模型继续影响当前建表定义，也容易误导开发者
认为这些历史数据库受到升级支持。

本决策调整开发期 Schema 来源和升级策略，不重新设计领域身份、表关系、
PostgreSQL `timestamptz` 时间模型或 JOOQ/Repository 边界。基线直接表达当前
领域模型；当前实现已经变化的状态约束不再保留旧值或编写转换。它修订 ADR 0032
中“按历史 SQL 生成多份 Flyway 资源”的构建条款。

## 备选方案

### 方案一：继续追加按日期版本化的迁移

能够升级任意已有数据库并保留数据，但需要长期维护当前并不承诺兼容的过渡模型、
回填逻辑和升级测试。

### 方案二：压缩一次历史后继续追加增量迁移

比现状短，但下一次开发期模型变化又会开始累积兼容脚本，仍未表达“旧开发数据可以
丢弃”的真实约束。

### 方案三：维护单一完整建表基线

让一份 SQL 直接描述当前目标 Schema。结构变化直接修改基线，已有开发数据库显式
重建，不提供原地升级和旧数据迁移。

### 方案四：应用每次启动时自动删除并重建数据库

无需人工清理，但一次配置错误就可能删除不应删除的数据，也会让普通应用启动具有
隐蔽的破坏性副作用。

## 决策

采用方案三：

- `gen/sql/flow/001_create_flow_tables.sql` 是开发期唯一、完整且可编辑的 PostgreSQL
  Schema 来源。
- 新增、删除或修改表、字段、约束和索引时，直接修改这份基线；不新增日期目录、
  ALTER 升级脚本、数据回填脚本或旧模型兼容分支。
- 基线必须能在空 PostgreSQL 数据库上一次创建全部当前对象，并能重复执行同一内容；
  `IF NOT EXISTS` 只用于重复执行安全，不承担修正旧 Schema 的职责。
- 基线变化后，开发者显式删除并重建已有开发数据库，再重新生成 JOOQ。旧 Schema
  和旧数据都不属于支持范围。
- 开发或部署人员在应用启动前手工执行基线；Server 不复制迁移资源，也不使用
  Flyway 创建、升级、清理或重建数据库。
- 历史迁移最终结果用于核对未发生领域变化的表、列、约束和索引；当前领域实现已经
  改变的约束直接使用当前值，不为旧值提供数据转换或双轨兼容。
- 当项目进入需要保留生产数据的首个发布阶段时，必须先新增 ADR，冻结当时基线并
  明确切换到追加式迁移、版本命名、升级验证和回滚策略。开发期历史数据库不自动
  获得生产升级承诺。

## 理由

- 数据库脚本直接表达当前模型，不再让已经淘汰的字段、状态和类型地址成为理解前置。
- Schema 变化、JOOQ 生成代码和 Repository 映射可以围绕同一当前事实校验。
- 显式重建把破坏性行为留在开发者控制下，避免应用启动自动删除数据库。
- 未来真正产生数据兼容要求时再冻结基线并建立迁移链，迁移成本与实际发布责任同步
  发生。

## 后果

- 已存在的旧 Schema 不能直接用于新构建，必须重建。
- 旧数据不会回填、转换或保留；需要的测试数据由测试夹具重新创建。
- 构建产物不包含 Flow 建表资源；人工基线只允许作用于 Flow 拥有的数据库。
- Schema 修改必须同时验证空库建表、重复执行、JOOQ 生成模型和相关 PostgreSQL
  集成测试。
- 过去的 ADR 和测试报告可以继续记录当时的迁移名称，但当前目录、手册和工作流只
  引用单一基线。
