# ADR 0010：领域对象统一使用静态 create 创建

## 状态

Accepted（Data Input 定义子类的局部例外由 ADR 0019 修订）

## 背景

作出本决策时，代码同时存在两种领域对象创建方式：部分领域类型已经提供静态
`create(...)`，部分调用链仍通过 `ExecutionFactory`、
`TaskDefinitionFactory` 等工厂类或工厂接口创建领域对象。

工厂层只是转发构造参数时会增加包、依赖注入和调用链复杂度，并使领域对象的
首次创建规则分散在领域类型与工厂实现之间。调用方也无法只通过领域类型本身确认
对象的初始状态、ID 生成和不变量。

## 备选方案

### 方案一：继续使用领域工厂

每种领域对象由独立 Factory 创建。便于通过依赖注入替换实现，但简单创建链路
需要额外类型，且领域创建规则容易泄漏到工厂。

### 方案二：领域类型自身提供静态 create

每个领域类型在自身的静态 `create(...)` 中完成普通业务创建。类型分派、解析和
持久化恢复继续使用各自明确的边界协议，但不承担普通领域创建规则。

## 决策

采用方案二：

- 聚合根、实体和值对象的普通业务创建入口统一为类型自身的
  `public static create(...)`。
- 领域对象构造方法使用 `private` 或 `protected`，领域类型外部不能直接
  `new`。
- `create(...)` 一次完成参数校验、不变量保护、防御性复制、技术 ID 生成和
  初始状态设置。
- Handler、Service 和领域编排代码直接调用目标领域类型的 `create(...)`；不得
  使用 Factory 复制、隐藏或绕过具体领域类型的创建规则。
- 具体领域子类型分别提供静态 `create(...)`。解析器和类型分派器可以选择具体
  类型，但必须调用该类型的 `create(...)`，不能复制构造规则。
- ADR 0019 确认的 `Input<T>` 及具体 Input 定义子类不向业务调用方提供主动
  `create(...)`，由 Flow 定义反序列化边界根据独立 DataType 一次形成完整对象。
  该例外不允许公共 Setter、半成品对象或调用方直接构造，也不扩展到 Task、
  Execution 等其他领域对象。
- Repository Adapter 使用静态 `rehydrate(...)` 恢复持久化状态。
  `rehydrate(...)` 沿用已有 ID、状态和版本，不触发首次创建规则。
- `deploy`、`parse` 等领域动词用于表达明确的业务转换，不作为通用领域对象
  工厂，也不能绕过目标类型的构造约束。
- `core/factories` 不再属于目标 Core 目录结构；复制领域创建规则的现有 Factory
  在相关业务链路迁移时删除。第三方客户端、连接或序列化等不创建领域对象的技术
  Factory 继续归对应 Adapter 或基础设施 Module 管理。

本 ADR 修订 ADR 0002 中通过 `ExecutionFactory` 创建 Execution 的调用链。

## 理由

- 创建规则与领域不变量保留在同一类型内，领域对象更容易理解和审查。
- 删除只做参数转发的工厂层，减少依赖注入、包结构和测试替身。
- `create(...)` 与 `rehydrate(...)` 明确区分首次业务创建和持久化恢复，避免
  回读时生成新 ID 或重置状态。
- 解析、类型分派和持久化仍保留独立边界，不会把外部格式或基础设施职责塞入
  领域对象。

## 后果

- `ExecutionFactory`、`TaskDefinitionFactory` 及其实现和调用方从生产与测试
  链路删除，不保留兼容接口或别名。
- Task 的动态类型分派只选择具体类型；Flow 负责身份和父子关系，分派器在普通
  创建和持久化恢复时分别调用具体 Task 子类型的静态 `create(...)` 与
  `rehydrate(...)`。
- 架构测试应禁止在生产 Core 中新增 `factories` 目录以及领域
  `*Factory` 类型，并验证领域构造方法不对外公开。
- 领域对象测试直接覆盖 `create(...)` 的合法输入、非法输入、初始状态和 ID
  生成；Repository 测试单独覆盖 `rehydrate(...)`。
