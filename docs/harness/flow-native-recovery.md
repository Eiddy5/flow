# Flow 原生机制与崩溃恢复验证

本轮以原生 Task、编排机制和触发器为测试对象。Flow 不承担审批、外派或待办业务；
既有以审批命名的流程只是历史组合样例。验证重点是执行状态、步骤结果和崩溃后的
继续推进，负载指标仅作为辅助。

已确认的恢复预期见 [UC-19](../uc/flow/UC-19%20原生流程运行崩溃恢复.md)，共 12 个
场景。常规机制和异常输入继续关联已有 UC；旧压力报告不作为新增崩溃场景的执行证据。

## 机制矩阵

| 机制 | 正常与异常状态检查 | 崩溃恢复检查 |
| --- | --- | --- |
| Sequence / 串行 | 按顺序消费前置结果；失败后停止后继 | 已确认步骤保持，原实例从未完成位置继续 |
| Route / 条件分支 | 条件命中、未命中、跳过路径和输出隔离 | 已确定路径与结果保持，不执行其他路径 |
| Parallel | 独立分支推进、不同完成顺序、全部就绪后汇聚 | 部分完成时退出，重启后保留进度并完成剩余分支 |
| Loop / LoopUntil | 轮次、条件退出、最大次数和失败收敛 | 不丢失已确认轮次，不串用不同轮次的结果 |
| SubFlow | 输入、子运行来源、子结果向父节点传递 | 子运行身份保持，完成结果能继续传递至父运行 |
| Pause | 等待、恢复结果、重复操作、恢复与取消竞争 | 等待事实保持，重启后仍可通过公开操作继续 |
| RunnableTask 重试 | 策略、次数与时间预算、成功/耗尽/取消 | 保留原尝试历史和计划，继续完成或合法失败 |
| Schedule / ScheduleOnDates | 定时条件独立命中、时间点和实例数量 | 已受理命中恢复推进，不新增同一命中的运行 |
| Webhook / FlowTrigger | 请求或上游终态触发、输入和运行关联 | 已受理触发恢复推进，关联关系和实例数量保持 |
| 终态 | 成功、失败、取消与节点结果一致 | 崩溃重启及迟到处理不把终态改回运行中 |

此表是验证组织方式，不是覆盖通过声明。每行分别关联已确认 UC、执行方法与结果；
没有真实故障注入证据的交接窗口保持未覆盖。不能把某个等待点恢复成功推广为
该机制所有保存、发布、消费窗口都能恢复。

## 崩溃证据要求

- 应用运行在测试专属子 JVM；控制端记录 PID、退出前可查询状态及稳定的运行标识。
- 到达本场景故障点后强制终止该 JVM，不运行其正常关闭回调。保存实际退出码和时间。
- 启动新的 JVM 连接同一专属数据库和 Broker；不得传递旧内存领域对象、清空消息、
  直接改数据库状态或手工重复发布命令来制造自动恢复。
- 恢复后通过公开入口重新查询实例和 Task，核对状态、输入输出、调用次数、轮次、
  父子关联，以及后继结果。不只检查根实例终态。
- 对中间交接窗口，必须提供确定到达窗口的证据；未命中窗口不算通过。
- 第一次失败保留现场并独立复验。恢复失败与测试夹具启动失败分别记录。

对外部调用已经发生但其结果尚未确认的窗口，分别记录调用次数与已确认结果；
本轮不凭空设定外部非幂等操作恰好执行一次。停机期间未受理的 Cron 是否补发、
父子取消级联和子流程退回规则也不自行扩展。

- 具名数据源空宿主库：同一容器内 `flow_host`。
- Pulsar：`flow-native-20260922-pulsar`，Broker `127.0.0.1:56662`，Admin `127.0.0.1:58092`。
- 环境变量：`/private/tmp/flow-native-20260922/environment.sh`。
- 原始证据：`build/native-validation/20260922-1730/`，与先前负载验证完全分开。

容器创建、基线初始化和清理沿用 [本地压力测试手册](flow-runtime-stress.md) 的限制，
替换成本轮名称和端口；不得使用全局 prune。所有网络目标必须检查为 loopback，
关闭远程配置与 Consul。测试应用退出只针对已记录的专属 PID。

收尾前导出真实状态、残留任务与消息数量，再归档数据库和删除这两个临时容器。
资源清理不代表流程已经正确恢复；失败现场与清理动作单独报告。

## 定向复跑

先按上面的隔离约束创建新环境并初始化基线，然后设置本次环境文件中的变量。
JDK 使用本地依赖要求的 25；`FLOW_STRESS_ENABLED=false`，禁止将普通场景回归
误切换成持续高负载。`FLOW_NATIVE_EVIDENCE_DIR` 应使用新的绝对目录，以免混淆轮次。

```bash
source /private/tmp/flow-native-20260922/environment.sh
export FLOW_NATIVE_EVIDENCE_DIR="$PWD/build/native-validation/recheck/processes"
export FLOW_NATIVE_CONTROL=false
./gradlew :scheduler:test --tests '*Uc19NativeRecoveryTest.s1SerialRecovery' --no-parallel --max-workers=1 --rerun-tasks
```

原测试容器清理后，上述环境文件不能直接使用，必须先重建专属本地依赖。
运行整个新增恢复矩阵时，将过滤条件改为 `*Uc19NativeRecoveryTest`；完整回归使用
`./gradlew test --continue --no-parallel --max-workers=1`，并保证本次测试任务未使用旧缓存。

同定义的无崩溃对照使用 `FLOW_NATIVE_CONTROL=true`，仅选择 S1–S5、S9–S11。
控制端释放外部调用等待后，原 JVM 继续运行并检查相同最终结果，不启动第二个引擎。
对照单独归档为 `control-*`，不得计入崩溃恢复 PASS；恢复测试必须显式改回 `false`。

## 2026-09-22 验证结论

完整逐场景证据见 [UC-19 测试报告](../test-reports/flow/UC-19-2026-09-22-2035.md)。
12 个场景为 4 PASS、8 FAIL；参数展开的 14 项为 5 通过、9 失败。同定义的
9 项无崩溃对照全部通过，不能据此提高崩溃恢复的通过数。

失败共同发生在真实业务调用中、任务 RUNNING 已保存的窗口：应用被强杀后，新 JVM
未在 35 秒内接续原任务，消息积压和未确认数均为 0。串行、分支、并行、循环以及
触发后运行分别复现；保留为共同恢复缺口在不同机制下的反例。
成功窗口为子 Pause 等待、子终态合并至父运行之前、重试等待和终态保持。
这些结果不覆盖所有保存/发布间隙、所有嵌套组合或数据库/Broker 自身崩溃。

模块回归为 38 项（29 通过、9 失败），其中原有 24 项全部通过。
全项目回归、最终残留资源、数据库归档与清理证据以报告中的实际执行记录为准。
