# 领域对象统一建模方法

## 适用范围

本规范适用于新增领域、拆分既有领域、调整聚合边界、增加生命周期能力，以及审查
领域模型是否完整。它规定所有领域都要遵循的建模顺序、判断方法和交付物，不定义
Flow、Task、Execution、PAUSE 或其他具体业务对象当前必须有哪些字段和状态。

具体领域对象、状态机、模块形态和运行协议属于架构决策，通过
[`../decisions/README.md`](../decisions/README.md) 查找对应 ADR。

## 1. 基本原则

- 领域对象从业务事实、术语和约束中产生，不能从数据库表、接口请求或现有类结构
  反推。
- 聚合边界由事务一致性和业务不变量决定，不能由外键、页面结构或调用方便决定。
- 领域对象始终处于合法状态，不创建可持久化的半成品。
- 聚合根保护聚合内实体，外部调用方不能绕过聚合根直接修改内部状态。
- 原始输入、Command、DTO、数据库 Record、查询 Projection、解析器和 Adapter
  不是领域对象。
- 业务版本、审计信息和并发版本是不同概念，必须分别建模。
- 领域通用建模方法放在本规范；某个领域最终选择什么模型记录为 ADR。

## 2. 固定建模顺序

新增或调整领域时必须按以下顺序完成，不得先建表或先写 Service，再补领域模型。

### 2.1 搜索现有能力与决策

开始前至少检查：

- `CONTEXT.md` 是否已有同义或相近术语。
- `docs/standards/` 是否已有适用的通用实现规则。
- `docs/decisions/` 是否已有相关聚合、生命周期、模块或存储决策。
- `docs/uc/` 是否已有正向、反向和变异场景。
- Domain、Repository、Service 和测试中是否已有相同业务能力。

不能只比较名称，还必须比较业务含义、有效性条件、身份、生命周期、事务边界和
版本规则。发现冲突时先明确冲突，再通过业务场景确认语义；需要改变已有架构选择
时先修订或新增 ADR。

### 2.2 定义领域术语

每个新领域概念先回答：

- 它在业务中是什么？
- 它明确不是什么？
- 哪些相近名称不再使用？
- 哪个业务事实证明它需要独立存在？

术语使用业务语言，不描述 Java 类、数据库表或接口结构。两个概念即使字段相似，
只要有效性条件、生命周期或不变量不同，就不能因为复用方便而合并。

### 2.3 确认对象角色

| 角色 | 判断标准 |
| --- | --- |
| 聚合根 | 有独立身份和生命周期，是事务一致性与 Repository 的入口 |
| 聚合内实体 | 有稳定身份，但生命周期完全由所属聚合管理 |
| 值对象 | 没有独立身份，按值表达业务含义，创建后不可变 |
| 领域服务 | 一条纯业务规则跨越多个聚合，且无法自然归属某个对象 |
| 边界能力 | 负责解析、序列化、外部调用或技术转换，不代表领域事实 |
| 状态值对象/枚举 | 表达有限业务状态、合法迁移和必要历史 |

只有聚合根建立独立 Repository。聚合内实体必须通过聚合根创建、查询和改变，不能
为了 CRUD 方便建立独立 Service 或 Repository。

### 2.4 划定聚合边界

每个候选聚合必须回答：

- 哪些规则必须在一次事务内保持一致？
- 哪个对象有权创建和修改内部对象？
- 内部对象能否脱离根对象独立存在？
- 其他聚合需要完整对象，还是只需要稳定 ID？
- 聚合关闭或删除时，哪些内部对象必须同时失效？

聚合根负责保护整个聚合的不变量。聚合外只持有其他聚合的稳定 ID；跨聚合协作由
CommandHandler 或明确的领域服务编排。

### 2.5 定义身份

每个实体和聚合必须明确：

- 技术身份 `id`。
- 可选业务标识，如 `key`、编码或名称。
- 跨版本时身份是否保持不变。
- 精确定位一个快照需要哪些字段。

技术 ID 的类型和生成规则统一遵守
[`project-development.md`](project-development.md)。业务标识不能替代技术 ID；
业务版本不能与并发版本混用。

### 2.6 设计生命周期与状态机

先写状态转换，再设计领域方法。每个有生命周期的对象至少明确：

- 唯一初始状态。
- 每个状态允许的业务动作。
- 每个动作的前置条件、状态变化和副作用。
- 终态及终态后的禁止行为。
- 哪些动作产生业务版本。
- 非法转换返回的领域错误。

如果某个“状态”下大量必填业务字段只能为空，或者两种状态具有完全不同的有效性
条件，应优先拆成不同领域对象，不能用状态和可空字段掩盖两个概念。

状态是否记录历史、状态时间从哪里获得以及具体迁移路线属于该领域的架构决策，
不在通用规范中预设。

### 2.7 选择领域字段

字段按以下类别逐项确认：

| 类别 | 内容 |
| --- | --- |
| 身份字段 | 技术 ID、租户 ID、稳定业务标识 |
| 业务字段 | 对象履行业务职责必须保存的事实 |
| 关系字段 | 聚合内实体或其他聚合的稳定 ID |
| 生命周期字段 | 状态、删除事实或业务版本 |
| 审计字段 | 操作者和创建、更新、删除时间 |
| 并发字段 | `lockVersion` 等纯技术并发信息 |

- 只保存对象拥有且无法从其他事实稳定推导的数据。
- 不把 Command、DTO、数据库对象或第三方解析节点整体塞进聚合状态。
- 集合在构造时防御性复制，对外只读。
- 创建后不允许变化的字段使用 `final`。
- 可空字段必须具有明确业务含义，不能用 `null` 兼容另一种对象形态。
- 派生值优先通过查询方法计算，除非它必须作为业务事实持久化。

### 2.8 设计领域方法和创建入口

领域方法表达业务语言并保护字段规则，不围绕单字段 Setter 设计。

方法分为：

1. 创建方法：类型自身的静态 `create(...)`，用于普通业务创建。
2. 行为方法：使用业务动词表达合法状态变化。
3. 查询方法：返回只读事实或派生判断。
4. 重建方法：静态 `rehydrate(...)`，只供可信 Repository Adapter 恢复状态。

统一要求：

- 构造方法为 `private` 或 `protected`，领域类型外部不能直接 `new`。
- `create(...)` 一次完成校验、不变量保护、防御性复制、技术 ID 生成和初始状态。
- `rehydrate(...)` 沿用已有 ID、状态和版本，不生成新身份，不触发首次创建规则。
- 不暴露 `setStatus`、`setDeleted`、`setOutputs` 等允许调用方绕过领域行为的公共
  Setter。
- 不得使用 Factory 复制、隐藏或绕过具体领域类型的创建规则。
- Parser、Dispatcher 和 Adapter 可以负责边界转换或类型选择，但最终调用领域
  类型确认的创建或重建入口，不能重新实现不变量。
- 第三方客户端、连接、序列化等不创建领域对象的技术 Factory 归对应 Adapter 或
  基础设施 Module，不受领域 Factory 禁止条款影响。

### 2.9 分离原始来源与有效领域对象

满足以下任一条件时，原始来源与目标领域对象应分离：

- 原始内容尚未解析或校验。
- 原始内容允许暂时无效，但目标对象必须始终有效。
- 原始内容和目标对象拥有不同字段、生命周期或版本规则。
- 转换失败时必须保留原始内容，且不能产生目标对象。

两者使用解析或映射关系，不能因为共享部分字段就使用继承。Parser 只负责格式
能力；目标聚合负责解释业务字段并形成完整合法对象。

### 2.10 区分版本、审计与并发

- 业务版本只在产生新的、可独立读取的业务事实快照时生成。
- 审计信息记录谁在何时执行业务动作，不等同于业务版本。
- 并发版本只用于 Repository 乐观锁或 CAS，不等同于业务版本。
- 失败操作不应占用业务版本，也不能留下部分审计或状态变化。
- 审计操作者和一般业务 timestamp 从可信服务器调用边界传入；领域专有例外必须由
  ADR 明确记录。

### 2.11 设计应用与持久化边界

- Service 提供用例入口，不承载领域状态机。
- Command 保存一次业务动作所需的调用输入。
- Handler 加载聚合、调用领域方法，并在同一事务中保存结果。
- Repository 以聚合根为单位加载和保存。
- Repository Adapter 使用 `rehydrate(...)` 恢复对象，不通过 Setter 拼装状态。
- 数据库对象、第三方解析节点和远程 DTO 不进入 Domain。
- 查询结构与领域结构实质不同时使用明确 Projection，不能建立与领域对象字段重复
  的 Snapshot 模型。

具体调用链、事务实现和持久化技术继续遵守对应项目规范与 ADR。

### 2.12 用场景验证模型

每个新领域进入实现前至少设计：

- 正向场景：每条合法业务动作和状态转换能够完成。
- 反向场景：非法状态、非法输入和越权操作被拒绝且没有部分修改。
- 变异场景：删除关键校验或绕过领域方法后测试必须失败。
- 身份场景：保存、重建、复制和状态变化后 ID 保持不变。
- 版本场景：成功版本动作递增，失败和非版本动作不递增。
- 聚合场景：外部代码无法绕过聚合根修改内部实体。
- 恢复场景：持久化往返恢复相同业务状态和顺序。
- 并发场景：重复命令或旧并发版本不会重复产生业务事实。

用户可观察预期只来自已确认 UC；架构和内部不变量使用独立技术测试保护。

## 3. 模型语义所有权与代码归属

类型归属由语义、不变量和演进规则决定，不能由当前谁调用、执行、实现或持久化
决定。

### Interface 与直接契约

- 描述某个业务概念可拥有能力的 Interface 归属于该业务概念所在 Module。
- 表达某策略所需外部能力的端口 Interface 归属于提出需求并定义契约的 Module；
  技术实现作为 Adapter 位于对应基础设施 Module。
- 仅服务于某个 Interface，且离开它就没有独立语义的 Context、Result、输入、
  输出和专用异常，跟随 Interface 归入同一 Module。
- 具有独立身份、生命周期或不变量的类型不能为了就近调用而并入消费者 Module。
- Adapter 专有请求响应、数据库 Entry、框架配置和传输信封不能反向成为上游业务
  Interface 的定义来源。

### 落包前检查

新增或移动领域类型及直接契约前必须完成：

1. **语义检查**：类型描述什么，哪个 Module 定义其含义和不变量？
2. **删除检查**：删除候选所有者或当前调用者时，类型随谁失去意义？
3. **替换检查**：替换执行器、数据库或消息系统后，类型是否仍然成立？
4. **依赖检查**：依赖是否保持“消费者或 Adapter -> 语义所有者”？

无法明确回答时，不得先创建临时 `common`、`shared`、`support` 或同义 Interface。
重要边界应通过架构测试保护；改变 Module 或公共 Interface 时记录 ADR。

## 4. 统一建模产物

每个新领域在编码前形成：

1. 规范术语及不再使用的名称。
2. 对象角色和聚合边界。
3. 包含字段和业务方法名的类图。
4. 生命周期状态转换表。
5. 明确编号的不变量列表。
6. 与其他聚合的关系和引用方式。
7. 业务版本、审计和并发版本的区分。
8. Repository、事务、解析和外部系统边界。
9. 正向、反向、变异、恢复和并发场景。
10. 与现有代码、标准和 ADR 的差距清单。

没有完成这些产物时，不应直接建立数据库表、Controller、Command 或 Service。

## 6. 完成检查清单

- [ ] 术语明确，且没有同义对象长期并存。
- [ ] 对象角色、聚合边界和 Repository 边界已经确认。
- [ ] 技术 ID、业务标识、业务版本和并发版本已经区分。
- [ ] 类图包含字段和业务方法。
- [ ] 生命周期、终态和非法转换完整。
- [ ] 每条不变量都有唯一负责的领域行为。
- [ ] 没有公共 Setter，也没有 Service 直接修改领域字段。
- [ ] 原始或未校验输入没有冒充有效领域对象。
- [ ] 失败操作不会留下部分状态或占用业务版本。
- [ ] 正向、反向、变异、恢复和并发场景已经设计。
- [ ] Interface、直接契约和 Adapter 的语义所有权明确。
- [ ] 具体模型选择已经记录或更新 ADR。
- [ ] 受影响的标准、UC、项目结构和测试已经同步。
