# UC 测试与校验规范

## 适用范围

本规范用于根据 `docs/uc/` 中的真实用户场景编写、执行和报告 UC 测试。UC 定义
用户操作和预期，测试负责验证当前代码框架是否满足这些场景。

## UC 与测试的关系

```text
一个 UC Markdown
  -> 一个主测试类
  -> 场景 S*
  -> 场景预期结果和结束状态
  -> 测试方法与断言
  -> 执行证据
  -> 场景结论
```

- UC 与主测试类严格一一对应。
- 主测试类覆盖 UC 全部场景，不能只测试当前已实现或成功路径。
- 每个预期结果和结束状态都必须能定位到断言或人工证据。
- 缺少任一证据的场景标记为 `NOT_COVERED`。
- 测试整体成功不等于全部场景通过，必须逐场景核对。

## 开始前必读

1. `docs/standards/development-basics.md`。
2. 本规范。
3. 目标 UC。
4. 相关领域标准和架构决策。
5. 生产代码、已有测试和测试环境说明。

UC 与生效规范冲突时停止编造预期，将场景标记为 `BLOCKED` 并交由 UC Agent
确认。

## 测试组织

### 测试位置

- 测试放在对应模块的 `src/test/java` 下。
- 测试包镜像被测公开入口的生产包。
- Service 驱动的 UC 放在对应 Service 包；HTTP 驱动的 UC 放在 Controller 包。
- 一个主测试类只负责一个 UC。
- 公共辅助类可以复用，但不能承载 UC 场景。

例如：

```text
server/src/main/java/org/cses/flow/core/services/flows/FlowService.java
server/src/test/java/org/cses/flow/core/services/flows/Uc01FlowLifecycleTest.java
```

主测试类注释记录 UC 路径：

```java
/**
 * UC: docs/uc/flow/UC-01 Flow 草稿生命周期与多租户管理.md
 */
class Uc01FlowLifecycleTest {
}
```

### 测试方法

- 方法名包含场景编号，例如 `s1ShouldCompleteDraftLifecycle`。
- 每个场景至少有一个可执行且未禁用的测试。
- 多个输入或状态分支使用参数化测试或多个同编号方法。
- `@Disabled`、空测试、TODO 和只调用不断言不算覆盖。
- 测试场景不得超出 UC；发现新场景时先交由 UC Agent 确认。

## 真实用户操作完整路径

Flow 运行场景必须模拟用户可以执行的公开操作：

- 正常 Flow：用户准备或选择 Flow、启动、查询结果并推进到完成终态。
- 失败或取消：用户查询到失败或取消终态；启动前拒绝则证明没有创建运行实例。
- 中间运行或等待状态只能用于观察，不能作为正常场景结束。
- PAUSE：被外派用户通过公开查询找到自己的具体任务，完成查询所得任务，再查询
  后续任务和流程状态，直至流程完成、失败或取消。
- 多个或并行 PAUSE：每个稳定等待点都重新查询，不能预取后续任务编号。

定义、草稿和部署场景虽然不创建运行实例，也必须使用公开用户操作，并通过重新
查询和清理形成闭环。

## 场景独立

- 每个测试方法准备自己的业务数据。
- 不依赖测试顺序或其他场景结果。
- 每个场景使用独立业务标识和运行实例。
- 不共享可变静态业务状态。
- 场景结束后不遗留会影响其他测试的资源或后台任务。

## PAUSE 持久化恢复

- 场景中可以观察运行和等待状态，但收尾后不得遗留运行实例或等待任务。
- 外派任务恢复不能复用启动流程时保留的内存对象。
- 关闭启动上下文后，由新的 server 上下文通过公开外派任务能力查询和完成任务。
- 阶段之间只通过持久化业务状态关联，不能传递内部对象。
- 测试报告记录最终仍在运行的流程和仍在等待的任务数量。

## 数据准备

- 测试数据名称体现 UC 和场景，例如 `uc01-s1-flow`。
- 通过公开输入创建数据，不能直接构造内部状态绕过业务入口。
- 时间、随机数和异步行为必须可控，不使用固定 `sleep` 等待结果。
- 重复、并发、多版本和多租户场景必须真实构造，不能只用 Mock 返回最终状态。

## 调用边界

- 写操作通过用户对应的公开 Service、Controller 或 HTTP 入口。
- 查询优先通过公开查询入口。
- 只有公开查询无法观察 UC 明确要求的持久化事实时，才允许只读
  Repository 或数据库查询补充证据。
- 不测试私有方法，不使用反射修改内部状态。
- Mock 只替换验收范围外的外部系统，不能替代本次领域规则和状态流转。

## 断言规则

### 映射场景预期

每个场景的以下内容都必须形成断言：

- `预期结果` 中的每一个可观察事实。
- `场景结束` 中的最终状态或资源清理结果。
- 拒绝场景中的明确错误和无副作用。

测试代码使用场景编号和清晰断言分组保留映射：

```java
// S1 预期：创建后可以按编号查询到草稿。
assertNotNull(draft);

// S1 场景结束：删除后不再作为可编辑草稿返回。
assertTrue(queryDraft(id).isEmpty());
```

### 必查维度

根据场景涉及对象检查：

- 状态和值。
- 数量和执行次数。
- 顺序和用户路径。
- 身份、归属和关联关系。
- 输入、输出和错误。
- 版本、租户和事务边界。
- 禁止副作用和资源清理。

不能只断言返回非空、HTTP 成功或一个最终状态。

### 异常

- 断言稳定业务错误，不依赖完整堆栈。
- 拒绝后继续查询，证明没有部分提交或越权副作用。
- 由有权用户完成场景要求的清理。

## 自动化与人工验证

- 能稳定自动化的场景优先使用自动化测试。
- 无法自动化时记录真实用户步骤、输入、环境、查询方式和实际结果。
- 人工证据必须可复核，不能使用“看起来正常”。
- 环境不可用时标记 `BLOCKED`，不能用静态代码阅读代替执行。

## 执行顺序

1. 编译目标模块。
2. 运行目标 UC 主测试类。
3. 单独重跑失败场景。
4. 运行目标模块测试。
5. 运行项目完整测试。
6. 涉及应用装配或 HTTP 时执行对应验证。
7. 逐场景填写结论和证据。

典型命令：

```bash
./gradlew :server:test --tests '*Uc01FlowLifecycleTest'
./gradlew :server:test
./gradlew test
```

## 场景结论

```text
PASS         场景已执行，全部预期和结束状态符合 UC
FAIL         场景已执行，至少一个结果不符合 UC
NOT_COVERED  缺少测试、断言或充分证据
BLOCKED      因环境、依赖或规范冲突无法执行
```

- 编译成功或测试类整体成功不能代替逐场景结论。
- 覆盖缺失使用 `NOT_COVERED`。
- 环境或规范冲突使用 `BLOCKED`。
- 实际结果违反 UC 使用 `FAIL`。

## 失败与反例

- FAIL 记录复现命令、输入、预期、实际和影响范围。
- 稳定实现问题分配 `CE-*` 并写入测试报告。
- 覆盖缺失和环境问题不是反例。
- 修复后使用相同用户场景和预期复验。
- 不修改 UC 使失败消失。

## 测试报告

报告路径：

```text
docs/test-reports/<uc-domain>/<UC-ID>-<YYYY-MM-DD-HHmm>.md
```

报告包含：

- UC 和唯一主测试类路径。
- 测试范围、时间和代码版本。
- 全部场景、测试方法、状态及预期结果证据。
- 执行命令与结果。
- 失败和反例。
- PASS、FAIL、NOT_COVERED、BLOCKED 数量。
- 结论和未解决事项。

每次执行创建新报告，不覆盖历史文件。

## 完成标准

- UC 与主测试类一一对应。
- 每个场景都有可执行测试。
- 每个预期结果和场景结束状态都有断言及证据。
- 场景独立、可重复且使用真实用户路径。
- 目标、模块和完整回归已经执行，或记录了阻塞原因。
- 稳定失败已有复现证据。
- 已生成新的测试报告。
