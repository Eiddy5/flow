# Flow 运行逻辑稳定性技术压力报告

所有15个技术压力调用均真实执行（8通过、7失败；其中4次是0受理的夹具启动/定义问题）。合计受理10337旅程，其中10334观察到目标终态、10330旅程断言通过；4个JDBC异常旅程及3个竞争反例均保留。正式连接池实现的本地八种工作负载合计10131受理/终态/旅程断言通过（smoke8、四阶1024、持续9099）。这些总数不混入UC场景数。

本轮发现已独立复验的 UC02 S7 恢复/取消竞争反例，完整回归还保留 State 迁移技术约束失败。因而不能宣称框架逻辑已经全面闭环稳定。以下较高并发及持续阶段只证明明确的八种工作负载在本机隔离环境下的结果。

## 范围和真实链路

源代码 `e189125 dirty`，所有既有生产、UC、断言保留。独立入口 `core/src/test/java/org/cses/flow/core/services/executions/RuntimeStressTest.java`，默认普通 test 不执行，显式 FLOW_STRESS_ENABLED=true 才启用。真实 FlowService/ExecutionService → Micronaut → Executor/Worker → PostgreSQL/Pulsar；外部 HTTP 业务服务由测试进程替代并独立记录副作用，身份Session使用既有测试构造。每阶段 2 个上下文竞争同一 Broker 订阅，4 个租户发布同 key 定义，公开查询校验每个 token、租户、步骤历史和所有派生实例集合。

- short：3 个顺序 HTTP 任务，逐步输出和公开步骤记录顺序。
- composite：顺序中嵌并行、Loop、条件命中/跳过、LoopUntil，核对循环迭代数、迭代编号、条件跳过分支和最终后继结果。
- pause：onPause 业务、准确步骤恢复、后继输出、重复提交拒绝且最终快照不变。
- race：同时恢复/取消，按已确认 UC02 S7 判断结果；发现反例后接续阶段明确排除。
- retry/exhaust：真实 Worker HTTP 第一次失败后重派成功，及两次失败重试耗尽；核对尝试次数和输出/失败终态。
- retry-cancel：等到 RETRY_WAIT 再取消，等待原计划时刻后再验证无额外业务调用。
- subflow：子流程 Pause 恢复到终态、父流程接续、租户和父子关联。
- replay：旧实例终止、替代实例从目标重新运行；向真实 Broker 投递旧实例 Resume 和 UPDATED 消息，完成替代实例并核对旧终态未变。

连接目标审计见 `local-targets-audit.json` 与持续阶段的 `local-targets.properties`，flow/default 实际池 JDBC URL 再通过运行时 getter 断言。config-client、Consul注册和服务watch关闭；持续阶段额外关闭consul.client.enabled，测试入口拒绝非loopback目标。这里始终是正式连接池实现的本地测试模式，没有使用生产环境。

正常阶段先等待运行命令/事件/延迟订阅 backlog 和 unacked 连续 3 次为零（最多 60 秒），再查询所有终态和实际 HTTP 副作用，断言没有重复业务调用、无跨租户污染、无多余派生实例。没有使用删除消息/数据来证明排空。此延迟观测覆盖本阶段计划和已注入消息，不能证明任意无限迟到窗口。

普通 UC 重启用例已实际关闭重建 ApplicationContext；长压力验证双上下文竞争，不等同于运行期间进程 kill、数据库/Broker 强制崩溃等故障注入。

## 环境、时间和指标口径

JDK25.0.4，测试 JVM max heap=1536 MiB，PG17（2CPU/1GiB）和 Pulsar4.0.7（4CPU/3GiB，严格延迟），Docker VM约8GiB；宿主20核/128GiB。URL及重跑方式见 `docs/harness/flow-runtime-stress.md`；全部真实命令使用 Gradle Wrapper，独立 init 仅设置阶段结果目录、日志、单 fork 和显式长压力禁缓存。没有连接业务库。每个阶段 XML/HTML、日志、CSV、summary、JVM和Broker快照均在 `build/stress-validation/20260922-1440/<phase>/`。

并发数是同时进行的用户旅程数，包含等待人工动作、重试延迟和迟到取消校验；不是HTTP请求速率。吞吐为目标终态数除以第一个旅程开始至最后一个worker完成的负载时间，不混入后续队列排空、最终全量核对或关闭耗时。启动到终态延迟在首次看到目标终态时固定；post-terminal校验在 journeyMillis 中。Replay 延迟包含先启动旧实例再重放并完成替代实例。所有分位仅针对有观测终态的样本，失败阶段需结合失败数，不能作为SLA。

原直连夹具每次查询通过 DriverManager 建连；本地池化阶段真实装配 org.x9.jooq.JOOQ 和具名 HikariUrlDataSource，每上下文 flow max16/min2，default max2/min1 指向独立空宿主库。`datasource-0/1.properties` 同时记录 `jooqUsesSameNamedPool=true`：测试实际断言 JOOQ 取得的 DataSource 与 flow 名称池是同一个对象，并排除 PostgresJooqTestAdapter。两种数据源配置及工作负载范围变化，以下表分开，不能拼成同一容量曲线。

该EOF时专属PG/Pulsar仍Running、OOMKilled=false、RestartCount=0，PG日志没有崩溃或连接数超限；事后TCP仅LISTEN也不能证明/排除峰值端口压力。原故障停发并关闭contexts后实际2个RUNNING/2个RETRY_WAIT、retry outbox pending0、scheduler outbox pending2、delay backlog6、command backlog1，不能将提前关闭消费者后的残留称为框架永久卡死。后续上下文会处理旧消息且旧HTTP服务已关闭，原阶段仍FAIL，不被后续全局收敛覆盖。保留 `infrastructure-stage4-failure.json`、`pg-stage4-failure.log`、`containers-stage4-failure.json`、`flow-stage4-failure.sql.gz`、`tcp-stage4-failure.json`。EOF根因未确认，不能称4并发是框架容量上限。

**CE-03：恢复与取消竞争使已取消 Pause 保留恢复输出（UC02 S7，FAIL）。** 当前 ACCEPTED UC 要求“恢复和取消最多只有一个生效”，既有 UC 主类同时断言取消后的 Pause 输出为空。普通主类基线、模块和完整回归均绿色；后续独立技术压力从相同公开入口同时提交 resume/cancel，发现两个命令都已受理，根最终 KILLED，Pause 同样 KILLED，但保留 decision 恢复值。请求受理不等于业务生效；反例判定依据是最终结果/输出及历史，不是仅仅两个请求都受理。

首次业务反例在 `mixed-c4-repro` 的样本 21（execution `6ab232de708f118bfb99d28c`、Pause `6ab232de708f118bfb99d28e`）：根历史 `PAUSED → RESTARTED → KILLING → KILLED`，Pause 历史 `PAUSED → RUNNING → KILLED`，输出仍含 `decision=sample-21-...`；onPause 子步骤已 SUCCESS。23 个旅程全部受理且到终态，其中 22 个旅程断言通过、1 个失败。

保持原 direct 配置与相同语义做独立定向 `race-c4-repro`：计划 64，失败后停止继续发起；实际 11 受理、11 KILLED、9 个旅程断言通过、2 次同一输出非空失败（样本 7：`6ab234817db0ca53b976ecd5`；样本 10：`6ab234827db0ca53b976ece1`），0 超时。两次均使用真实双 ApplicationContext、PostgreSQL/Pulsar、4 并发，不修改状态；取消后最终查询存在输出的反例已经复验。
