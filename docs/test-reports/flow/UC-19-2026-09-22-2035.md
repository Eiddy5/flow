## 测试范围

验证原生串行、Route、Parallel、Loop、LoopUntil、SubFlow、Pause、RunnableTask 重试以及四类触发器受理后的崩溃恢复。Flow 不提供审批业务，测试使用中性输入和确定输出。

控制端只运行范围外的 HTTP 业务样本，不创建 Micronaut 引擎或共享订阅消费者。每个场景的准备 JVM 独占真实运行组件；公开查询确认故障窗口后，控制端调用该 `Process` 的 `destroyForcibly()`，记录实际 PID、退出码 137 和退出时间。恢复使用全新 JVM、原数据库和 Broker；不传递旧领域对象、不修改数据库状态、不手工补发启动或调度事件。

写操作通过 FlowService、ExecutionService、WebhookTriggerService；触发时间、队列与持久化使用真实组件。本轮 Webhook 以 Core 公开受理入口验证恢复，不将其描述为 HTTP/AuthX 认证验收。S7 的测试子类仅在生产 `SubFlowExecutionHandler.complete` 调用前设置等待门：已确认子运行终态持久化、父调用仍 RUNNING 后强杀。恢复阶段完整调用原方法。它没有覆盖“父结果已保存、父 UPDATED 尚未发布”等其他窗口。

外部样本在 B 的真实 HTTP 调用中等待，A 的成功结果已经保存。该窗口没有要求未确认的外部操作恰好调用一次；断言仅要求已确认完成的步骤不重跑、未完成部分能够继续以及最终结果和调用次数符合 UC。

## 失败与反例

### CE-UC19-01：RunnableTask 已持久化 RUNNING 后进程崩溃，原步骤未继续

- 输入：S1 串行 A/B/C、S2 已命中条件路径、S3 部分完成并行、S4/S5 第二轮中途，以及 S9/S10/S11 已受理触发的运行。
- 故障点：A 或此前轮次已 SUCCESS；B 的真实 Worker 调用进入外部 HTTP 样本并阻塞，B 的 RUNNING 和未完成尝试已持久化；后继 C 尚无运行记录。
- 操作：对该独占引擎 JVM 强杀，实际退出码 137；新 JVM 使用同一数据库与 Broker，用户不重新启动或手工重发事件。
- 预期：原身份、版本、输入与已确认结果保持；未完成的 B 正确接续，C 消费正确输出后成功结束。
- 实际：新 JVM 观察 35000 毫秒后根实例和 B 仍 RUNNING，后继未执行；已完成结果保留。恢复后 Broker 对应订阅的 backlog/unacked 为 0，不能解释为只是在等待尚未投递的原消息。
- 复现：`./gradlew :scheduler:test --tests '*Uc19NativeRecoveryTest.s1SerialRecovery'`，其余方法见场景表与逐方法复验日志。
- 影响：本轮已测的执行中 Worker 窗口；不推广为任意状态或所有消息交接均失败，也不将 35 秒观察直接称为永久卡死。
- 源码解释辅助：ExecutorEventMessageHandler 在 dispatch 后保存 RUNNING，再同步调用 Worker；重投调度只领取 CREATED。源码解释不替代上述运行证据。

### 全量回归关闭期阻塞（独立技术观察）

本次 `full-regression` 在 `SubFlowExecutionIntegrationTest.completesTwoSubFlowsAndWorkerInSameParallelBatch` 的夹具关闭阶段停止输出（20:36:11，Asia/Shanghai）。`full-core-thread-dump.txt` 与间隔复核 `full-core-thread-dump-recheck.txt` 均显示：Test worker 在 `WorkflowUcFixture.closeServer → ApplicationContext.stop → TriggerRuntime.shutdown` 等待 TriggerRuntime monitor；scheduled-executor-thread-2 持该 monitor，在 `publishPending → PulsarQueue.emit → Pulsar.getProducer → ProducerBuilderImpl.create → CompletableFuture.get` 等待。

这是关闭期同步等待观察，不宣称已证明 Java monitor 死锁或确定永久卡死。为了让 `--continue` 执行其他模块，核验其命令行确为本轮 core `Gradle Test Executor 15` 后仅 SIGKILL PID 90100，记录 `full-core-worker-termination.json`；core 未正常完成，任何部分 XML 均不能补成完整 core 通过数。生产代码与夹具关闭协议未改。独立方法有界复验 22 秒通过（`single-subflow-recheck.log`、`single-subflow-recheck.json`），说明该问题依赖全量运行条件，本轮尚未确定稳定复现条件。

随后从首次 Core XML 和源文件清单选择未执行的 53 个测试类，`core-remainder` 在同一临时环境完整运行且 263 项全通过。两轮合计覆盖 90 个 Core 测试类，但它们是不同批次，不能合并为一次无中断的全量构建通过。

`full-regression` 的 Scheduler 另有 `SchedulerReliabilityTest.duplicateTriggerEventKeepsOriginalExecutionIdentity` 一项失败，断言为调度事件重投后 Broker 未完成 ACK。对应 XML 日志出现此前 Core 测试类型 `TestWorkflowTask` 无法注册为插件的反序列化异常；同一 Scheduler 模块先前独立回归此方法通过。该项单独记录为跨模块共用 Broker 历史事件下的回归失败，不能计入 UC19，也不能仅凭日志把原因归结为新生产代码。
