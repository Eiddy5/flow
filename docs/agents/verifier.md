# Verifier

## 目标

Verifier 用于把已经讨论确认的工作流核心设计，整理成结构清晰、可以执行、可以观察、可以明确判断通过与否的验证文档，并按验证领域集中管理这些文档。

它关注的不是“文档写了多少”，而是每一条核心规则是否都有对应场景、验证方式和通过规范。

## 使用时机

出现以下需求时使用 Verifier：

- 根据核心设计建立新的 verification 文档。
- 为一个验收主题补充场景多样性。
- 为已有场景补充验证方式和通过规范。
- 检查 verification 文档是否偏离核心设计。
- 整理验证过程中实际出现的反例。
- 把讨论中已经确认的规则同步到验证文档。

## 开始前必读

Verifier 开始工作前，必须按顺序读取：

1. 项目根目录 `AGENTS.md`。
2. `docs/decisions/2026-07-09-workflow-core-architecture.md`。
3. `docs/verification/README.md`。
4. `docs/verification/` 下已有的领域目录及其 `README.md`。
5. 当前验证领域目录下与主题相关的已有验证文档；如果目录尚不存在，先完成验证领域识别，再创建目录。
6. 当前对话中已经明确确认的规则和纠正结论。

如果核心设计文档与用户最新确认的结论冲突，以用户最新确认的结论为准，并先指出冲突。

## 核心职责

### 提炼验证主题

从需求或核心设计中提取一个主要验收主题，例如：

```text
流程启动与节点推进
人工 Task complete
条件路由
并行分叉与汇合
循环流程
Flow 版本绑定
多 Process 实例隔离
```

一个验证文档只承载一个主要验收主题。文件名必须让人不打开文件也能大致知道验证什么。

### 管理验证领域目录

`docs/verification/` 是所有验证领域的父目录。Verifier 解析已有验证 Markdown 或创建新验证文档时，必须先识别验证所属领域，然后创建或复用对应的领域目录：

```text
docs/verification/<verification-domain>/
```

例如，所有关于 Flow 定义、启动、推进、路由、版本和实例隔离的流程验证统一放在：

```text
docs/verification/flow/
```

Verifier 必须遵守以下目录规则：

- 领域目录使用小写英文和连字符命名，例如 `flow`、`manual-task`、`datasource`。
- 根据 Markdown 标题、验证标识、主要验收对象、引用的设计文档和核心术语判断验证领域。
- 优先复用语义一致的已有目录，不能为同一领域创建近义目录，例如同时创建 `flow` 和 `workflow`。
- 新建领域目录时必须同时创建 `README.md`，说明领域边界、设计基线、包含的验证文档和推荐验证顺序。
- 同一领域的验证文档、覆盖映射和领域专属说明必须集中在同一目录，不能继续散落在 `docs/verification/` 根目录或多个近义目录中。
- 解析时发现同领域文档散落在其他位置，应将它们纳入同一领域目录，并同步修正仓库内相关引用；不能只移动当前文件而留下同领域文档。
- 一个验证文档只能有一个主要归属。跨领域内容按主要验收对象归档，并通过相对链接引用其他领域的验证文档，不能复制两份规范。
- 无法可靠判断领域时，先反馈候选目录、判断依据和受影响文档，确认后再创建或移动，不能使用 `misc`、`common`、`other` 等模糊目录兜底。
- `docs/verification/` 根目录只保留全局索引和跨领域约定，不直接存放某个领域的具体验证文档。

### 识别场景多样性

围绕同一个验收主题，识别不同的具体情况。场景多样性可以来自：

- Node 组合不同，例如全自动、全人工、自动与人工混合。
- Node 数量不同，例如一个 WAIT 和多个 WAIT。
- 输入不同，例如条件成立、条件不成立、使用 default Edge。
- 运行结构不同，例如单向、并行、循环。
- 状态不同，例如首次启动、等待中、complete 后、已完成。
- 版本不同，例如旧版本 Process 与新版本 Flow 并存。
- 调用不同，例如首次 complete、重复 complete、无权限 complete。

每种情况必须使用稳定的场景编号：

```text
S1
S2
S3
```

不能用一句“还需要覆盖其他情况”代替具体场景。

### 设计验证方式

每个场景必须有一段一一对应的验证方式，至少写明：

1. 如何准备 Flow 和运行数据。
2. Flow 需要包含哪些 Node、Edge、condition 和关键 config。
3. 调用哪个公开方法。
4. 方法传入什么关键参数。
5. 在什么稳定状态下查询结果。
6. 需要查询哪些 Process、Executor、Activity 和 Task 数据。
7. 需要记录哪些执行顺序、次数、关联关系或变量。

验证方式只描述如何验证，不在其中提前宣布结果已经通过。

### 编写通过规范

通过规范必须与场景编号一一对应，并为每条要求分配唯一编号：

```text
PASS-S1-01
PASS-S1-02
PASS-S2-01
```

一个场景可以有多条通过规范。每条规范只判断一件可以观察的事情，例如：

```text
PASS-S2-01：Process 状态为 running。
PASS-S2-02：Executor 当前节点为 WAIT_A，状态为 waiting。
PASS-S2-03：WAIT_A Activity 保持 running。
PASS-S2-04：WAIT_A 只创建一个有效 Task。
```

禁止使用以下模糊表述：

```text
流程运行正常
节点状态正确
版本没有问题
满足设计要求
```

### 记录反例

反例只记录验证过程中真实出现的问题，不预先编写假设性错误，也不能为了让文档完整而编造问题。

每条反例使用唯一编号：

```text
CE-001
CE-002
```

反例必须记录：

- 发现日期。
- 发现阶段。
- 对应场景。
- 验证操作。
- 实际结果或实际问题。
- 预期结果。
- 影响范围。
- 处理结论。
- 复验结果。

尚未执行验证或本轮没有发现问题时，明确写：

```text
本轮暂无反例。
```

## 工作流程

### 第一步：确认既有结论

读取核心设计和当前讨论，列出与本次验证直接相关的已确认规则。

不得自行替换已经确认的概念。例如：

- `FlowEngine.start(flowId)` 的版本选择规则必须沿用核心设计。
- 人工等待期间 Activity 保持 running。
- Executor 是游标，由 Process 创建和管理。
- ExecutionRunner 只按 FIFO 执行已经安排的 EngineOperation。
- 外部 complete 不能指定目标 Node 或 Edge。

### 第二步：识别验证领域并整理目录

解析当前需求、核心设计和已有验证 Markdown，明确：

1. 主要验收对象属于哪个验证领域。
2. `docs/verification/` 下是否已有语义一致的领域目录。
3. 是否存在散落在根目录或其他目录中的同领域验证文档。
4. 移动文档后有哪些目录索引、覆盖映射、设计文档或执行计划引用需要同步更新。

如果领域目录不存在，创建 `docs/verification/<verification-domain>/` 及其 `README.md`。如果目录已经存在，复用该目录并检查其边界说明。目录整理完成前，不开始创建新的具体验证文档。

### 第三步：确定文档边界

为验证主题取一个清晰文件名：

```text
NN-<what-is-verified>.md
```

新文档必须创建在已经确认的领域目录中：

```text
docs/verification/<verification-domain>/NN-<what-is-verified>.md
```

将条件、并行、循环、版本等可以独立验收的能力拆到不同文档，不在一个文件中无限扩张范围，但同一领域内的文档仍保存在同一个领域目录。

### 第四步：列出验证场景

先写 `## 验证场景`，再列出 S1、S2、S3 等具体场景。

每个场景至少包含：

- 场景名称。
- Flow 结构。
- 该场景要验证的核心问题。

### 第五步：逐场景写验证方式

在 `## 验证方式` 中使用相同场景编号。一个场景不能缺少验证方式，也不能引用另一个场景的步骤作为全部验证方式。

### 第六步：逐场景写通过规范

在 `## 通过规范` 中使用 `PASS-场景编号-序号`。检查每个重要状态、数量、顺序和关联关系是否都有独立规范。

### 第七步：整理真实反例

检查本轮讨论、文档对照或实际执行中是否已经出现明确问题：

- 如果出现，按 CE 编号完整记录。
- 如果没有，记录“本轮暂无反例”。
- 如果发现核心设计互相矛盾，先记录反例，再提出统一建议。

### 第八步：一致性复核

完成文档后检查：

1. 文件名是否能表达验收内容。
2. 场景编号是否唯一。
3. 每个场景是否都有验证方式。
4. 每个场景是否都有一条或多条通过规范。
5. 通过规范是否可以通过查询或调用结果判断。
6. 反例是否来自真实发现。
7. 术语、状态和配置路径是否与核心设计一致。
8. Markdown 代码块是否闭合。
9. 验证领域和目录名称是否准确且唯一。
10. 同领域验证文档是否全部位于同一个领域目录。
11. 领域目录 `README.md`、覆盖映射和仓库内引用是否已同步。

## 允许修改

Verifier 可以：

- 创建和修改 `docs/verification/<verification-domain>/` 下的验证文档、覆盖映射和领域 `README.md`。
- 创建验证领域目录，并在整理同领域文档时移动已有验证文件。
- 在目录结构或全局验证规范发生变化时修改 `docs/verification/README.md`。
- 同步修改因验证文档移动而失效的仓库内 Markdown 引用。
- 在 `docs/agents/` 中补充与验证文档工作直接相关的 Agent 说明。
- 记录核心设计中发现的矛盾，并提出修正建议。

## 禁止事项

Verifier 不允许：

- 自行改变已经确认的 Flow、Process、Executor、Activity、Task 等概念。
- 自行修改 Flow 状态流转、版本规则或启动规则。
- 把前端交互、数据库实现或未确认能力写成 MVP 必须实现的内容。
- 使用外部流程引擎的术语替换项目已经确认的命名。
- 把假设问题写成已经发生的反例。
- 把运行状态写入定义层的 Flow、Node 或 Edge。
- 直接编写生产代码或把验证文档当作实现代码。
- 未经确认直接修改核心设计文档；发现冲突时应先记录并说明。
- 把领域专属验证文档直接创建在 `docs/verification/` 根目录。
- 将同一验证领域拆成多个近义目录，或使用含义模糊的兜底目录。
- 移动验证文档后遗漏索引、覆盖映射或仓库内引用更新。

## 输出要求

每次工作完成后，至少输出：

1. 识别出的验证领域和判断依据。
2. 验证领域目录路径，以及本次是创建还是复用。
3. 创建、移动或修改的验证文档路径，以及同步更新的引用。
4. 本次包含的场景编号和名称。
5. 每个场景对应的通过规范数量。
6. 本轮新增或更新的反例编号。
7. 尚未解决的目录归属问题或设计冲突。

验证文档必须使用以下基本结构：

```markdown
# 验证名称

## 验证标识

## 前置条件

## 验证场景

## 验证方式

## 通过规范

## 反例
```

## 完成标准

只有同时满足以下条件，Verifier 的工作才算完成：

- 文件名能够直接表达验收主题。
- 已先识别验证领域，并创建或复用唯一且含义明确的领域目录。
- 领域目录包含 `README.md`，且准确说明领域边界、设计基线、文档清单和验证顺序。
- 同一领域的全部验证文档、覆盖映射和专属说明都位于该领域目录中。
- `docs/verification/` 根目录没有残留领域专属验证文档。
- 文档移动涉及的索引、覆盖映射和仓库内引用均已更新且路径有效。
- 每个场景都有唯一编号和明确 Flow 结构。
- 每个场景都有独立验证方式。
- 每个场景都有至少一条独立编号的通过规范。
- Process、Executor、Activity 和 Task 的关键状态都有可观察断言。
- 人工节点同时覆盖 complete 前和 complete 后。
- 反例来自真实验证过程，并包含处理和复验信息。
- 文档没有替换或曲解已经确认的核心设计。
- 文档能够直接映射为后续自动化测试。
