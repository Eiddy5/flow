# UC-18 用户重试失败的流程步骤

## 验证标识

- UC：`UC-18`
- 状态：`ACCEPTED`
- 领域：`flow`
- UC 类型：`流程运行`
- 需求基线：`用户确认的任务重试策略、实际再次执行、耗尽后失败处理及再次调用前的提交等待状态@2026-10-12`
- 依赖：`UC-01、UC-02`

## 验证目标

用户为直接执行业务操作的步骤配置固定、指数或随机重试策略，启动流程后能够查询
每次实际尝试、下一次计划时间和最终结果。临时失败恢复后继续后续步骤，次数或时间
预算耗尽后明确失败；服务重启、重复结果和取消不会使重试历史或最终结果失真。
计划到期后，用户可以区分再次调用的已提交待执行与正在执行状态；下一次尝试的
执行开始时间对应实际领取确认，等待领取本身不再增加业务重试次数。

## 验证场景

### S1 固定间隔重试后成功

- 参与用户：流程编排用户和发起用户
- 开始状态：已发布流程包含前置步骤、业务操作步骤及消费其结果的后置步骤；业务操作前两次失败、第三次成功，配置最多执行 3 次、固定间隔 1000 毫秒，不启用重试成功警告
- 用户操作：发起用户启动流程，查询业务操作的失败、等待重试、到期后的提交等待及每次实际调用结果，再查询后置步骤和最终结果
- 预期结果：业务操作实际执行 3 次，每次失败后计划等待 1000 毫秒，到期前不再次调用；到期后再次调用先显示已提交待执行，领取确认后才显示正在执行并记录该次尝试的执行开始时间，不把提交时间当作执行开始时间；提交等待不额外消耗业务重试次数；流程和业务步骤的运行编号保持不变，三次尝试的编号、开始与结束时间、结果及失败原因均可查询；等待期间流程仍在运行，后置步骤不提前执行；第三次成功后后置步骤只消费成功结果并执行一次，前置步骤不重跑
- 场景结束：流程成功完成，没有等待重试或活动步骤

### S2 指数退避达到间隔上限

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作前四次失败、第五次成功；配置最多执行 5 次、初始间隔 1000 毫秒、倍率 2、最大间隔 3000 毫秒，后置步骤消费业务成功结果
- 用户操作：用户启动流程，逐次查询失败时间、下一次计划时间、尝试历史和后置结果
- 预期结果：四次重试的计划间隔依次为 1000、2000、3000、3000 毫秒，均从前次失败开始计算，到期前不再次调用；业务操作实际执行 5 次，之前的失败记录保留；只有第五次成功后后置步骤才执行一次
- 场景结束：流程成功完成，没有等待重试或活动步骤

### S3 随机间隔保持在配置范围

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作前两次失败、第三次成功；配置最多执行 3 次、随机最小间隔 1000 毫秒、最大间隔 3000 毫秒，后置步骤消费业务成功结果
- 用户操作：用户启动流程，在每次等待期间多次查询同一业务步骤的下次计划时间，再查询全部尝试和后置结果
- 预期结果：每次随机计划间隔均处于配置范围；同一次等待的计划时间不会因反复查询而变化，到期前不再次调用；业务操作实际执行 3 次，后置步骤只在成功后执行一次
- 场景结束：流程成功完成，没有等待重试或活动步骤

### S4 次数耗尽后明确失败

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作始终失败，配置最多执行 3 次及固定间隔 1000 毫秒，成功后才执行后置步骤
- 用户操作：用户启动流程，查询每次失败和等待，最终查询业务步骤、后置步骤及流程结果
- 预期结果：最多执行 3 次包含首次调用，第三次失败后不再安排第四次；三次失败原因和尝试历史均保留；业务步骤和流程最终失败，不产生成功输出，后置步骤不执行
- 场景结束：流程已失败，没有等待重试或活动步骤

### S5 时间预算耗尽后停止安排重试

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作首次会失败，配置最多执行 10 次、固定间隔 2000 毫秒、重试时间预算 1000 毫秒，成功后才执行后置步骤
- 用户操作：用户启动流程，查询首次尝试结果、后续尝试数量和流程最终结果
- 预期结果：时间预算从首次尝试开始计算；下一次计划时间超过预算时不再安排重试，即使次数仍有余额；业务操作只调用一次，保留失败原因，后置步骤不执行；预算只约束后续尝试的计划，不将其当作单次业务操作的强制中断时间
- 场景结束：流程已失败，没有等待重试或活动步骤

### S6 重试成功后保留警告

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作首次失败、第二次成功，配置最多执行 2 次、固定间隔 0 毫秒并启用重试成功警告，后置步骤消费成功结果
- 用户操作：用户启动流程，查询两次尝试、业务步骤警告和后置步骤结果
- 预期结果：业务操作实际调用两次；第二次成功后保留首次失败历史并显示重试成功警告，仍提供成功输出供后置步骤消费；后置步骤执行一次，警告不使流程停留在等待状态，也不把最终失败视为成功
- 场景结束：流程已结束，业务步骤保留重试成功警告，没有等待重试或活动步骤

### S7 等待期间服务重启后继续原计划

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布流程的业务操作首次失败、第二次成功，配置最多执行 2 次及固定间隔 10000 毫秒
- 用户操作：发起用户启动并查询到等待重试及下一次计划时间；运维用户在等待期间重启服务；发起用户重新按原运行编号查询，等待重试完成后查询历史及后置结果
- 预期结果：重启后仍能查询原运行和首次失败记录，计划时间保持不变；到期后继续第二次实际调用，不要求用户重新启动流程；只保留两次尝试且前置步骤不重跑，后置步骤只消费成功结果一次
- 场景结束：原流程成功完成，没有额外运行实例、等待重试或活动步骤

### S8 等待期间取消后不再调用业务操作

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作首次失败，配置最多执行 3 次及固定间隔 10000 毫秒
- 用户操作：用户启动流程，查询到等待重试后取消该运行，查询确认取消成功；到原计划时间后再次查询尝试历史、业务调用记录和后置步骤
- 预期结果：取消后保留首次失败历史，不发起第二次业务调用；原计划到期不使流程恢复运行，后置步骤不执行，流程取消结果保持不变
- 场景结束：流程已取消，没有等待重试或活动步骤

### S9 重复和迟到结果不改变当前尝试

- 参与用户：流程发起用户
- 开始状态：已发布流程的业务操作首次失败、第二次成功，配置最多执行 2 次；业务调用结果在通信恢复时可能重复或迟到
- 用户操作：用户启动流程，查询首次失败后的等待；在首次失败结果重复到达、第二次成功后首次结果又迟到的情况下，持续查询同一运行、尝试历史、后置步骤与最终结果
- 预期结果：重复失败不额外消耗尝试次数，不增加重试调用；迟到的首次结果不覆盖第二次成功结果，不使流程再次失败；只保留两次实际尝试，失败历史可追溯，后置步骤只消费第二次成功结果一次
- 场景结束：流程成功完成，没有额外运行实例、等待重试或活动步骤

### S10 未配置重试或最多一次时直接失败

- 参与用户：流程发起用户
- 开始状态：两个独立已发布流程的业务操作都会失败，一个未配置重试，另一个配置最多执行 1 次；两者均有成功后才执行的后置步骤
- 用户操作：用户分别启动两个流程，按各自运行编号查询尝试历史、失败原因和后置步骤
- 预期结果：两个流程的业务操作均只调用一次，首次失败后直接显示最终失败，不安排再次调用；各自失败原因可查询，后置步骤均不执行
- 场景结束：两个流程均已失败，没有等待重试或活动步骤

### S11 拒绝非法重试配置

- 参与用户：流程编排用户
- 开始状态：用户准备包含业务操作步骤的独立流程草稿，分别把最大执行次数设为 0 或负数，或把固定重试间隔设为负数
- 用户操作：用户保存并查询各草稿，分别尝试发布；每次拒绝后重新查询草稿及正式版本，最后删除这些草稿
- 预期结果：每个非法配置都被明确拒绝发布，不产生可运行版本或业务调用；拒绝不改变已保存草稿内容
- 场景结束：本场景草稿已删除，没有创建运行实例或活动步骤

### S12 等待重试不阻止其他并行分支

- 参与用户：流程发起用户
- 开始状态：已发布流程包含两个并行分支；一个业务操作首次失败、第二次成功并配置固定间隔 10000 毫秒，另一个分支可独立成功；汇总步骤需要两个分支成功结果
- 用户操作：用户启动流程，在业务操作等待重试期间查询两个分支，再查询重试结果、汇总结果和最终状态
- 预期结果：等待期间另一个分支可以完成，汇总步骤尚未执行；到期后仅失败业务操作再次调用，已经成功的分支不重跑；重试成功后汇总步骤消费两个结果并只执行一次
- 场景结束：流程成功完成，没有等待重试或活动步骤

## 验证方式

### S1

1. 用户选择已发布的固定间隔流程，准备前两次失败、第三次成功的合法业务数据并启动。
2. 用户通过公开运行查询识别业务步骤，逐次核对尝试编号、起止时间、失败原因和下次计划时间；计划到期后查询已提交待执行与领取后的正在执行，核对执行开始时间不是提交时间，并对照业务调用记录确认实际调用三次。
3. 用户查询等待期间的后置状态以及成功后的消费结果，确认编号不变、前置不重跑、后置只执行一次。
4. 用户查询确认流程成功完成，没有等待重试或活动步骤。

### S2

1. 用户选择指数策略流程，准备前四次失败、第五次成功的业务数据并启动。
2. 用户通过公开运行查询逐次核对失败时间与下次计划时间，确认四次计划间隔为 1000、2000、3000、3000 毫秒，业务调用均未提前开始。
3. 用户对照业务调用记录确认共五次调用、失败历史保留且后置步骤只消费成功结果一次。
4. 用户查询确认流程成功完成，没有等待重试或活动步骤。

### S3

1. 用户选择随机策略流程，准备前两次失败、第三次成功的业务数据并启动。
2. 用户通过公开运行查询反复读取每次等待的计划时间，核对同次计划稳定且相对前次失败的间隔在 1000 至 3000 毫秒范围内。
3. 用户对照业务调用记录确认到期前未调用、共调用三次，并查询后置步骤只消费成功结果一次。
4. 用户查询确认流程成功完成，没有等待重试或活动步骤。

### S4

1. 用户选择最多执行三次的流程，准备始终失败的业务数据并启动。
2. 用户通过公开运行查询核对三次失败的编号、原因和等待过程，并对照业务记录确认仅三次调用。
3. 用户查询最终失败及不存在第四次计划，核对没有成功输出、后置步骤未执行。
4. 用户确认流程已失败，没有等待重试或活动步骤。

### S5

1. 用户选择间隔 2000 毫秒、预算 1000 毫秒且最多执行十次的流程，准备会失败的合法数据并启动。
2. 用户通过公开运行查询首次开始时间与失败结果，确认下一次计划将超出预算。
3. 用户查询仅一次调用和保留的失败原因，确认没有再次执行或后置结果。
4. 用户确认流程已失败，没有等待重试或活动步骤。

### S6

1. 用户选择启用重试成功警告、零间隔且最多执行两次的流程，准备首次失败、第二次成功的数据并启动。
2. 用户通过公开运行查询两次尝试与警告，并对照业务记录确认实际调用两次。
3. 用户查询首次失败记录和成功输出，确认后置步骤消费成功结果一次。
4. 用户确认流程已结束且业务步骤警告仍可查询，没有等待重试或活动步骤。

### S7

1. 用户选择固定间隔 10000 毫秒且最多执行两次的流程并启动，查询并记录运行编号及下一次计划时间。
2. 运维用户在等待期间重启服务；发起用户重启后通过公开运行查询重新定位原实例和业务步骤。
3. 用户核对原失败历史和计划时间不变，再查询第二次实际调用成功、前置不重跑及后置唯一结果。
4. 用户确认原流程成功完成，没有额外实例、等待重试或活动步骤。

### S8

1. 用户启动目标流程，通过公开运行查询确认首次失败且正在等待下一次调用。
2. 用户通过公开取消能力取消所查询实例，并重新查询确认取消成功。
3. 到原计划时间后，用户重新查询取消状态、首次失败历史及业务调用记录，确认没有第二次调用或后置结果。
4. 用户确认流程保持取消，没有等待重试或活动步骤。

### S9

1. 用户启动允许最多执行两次的流程，准备首次失败、第二次成功且结果可能重复到达的业务过程。
2. 用户通过公开运行查询首次失败及等待，在重复结果到达后核对次数和计划未额外增加。
3. 用户查询第二次成功结果，在首次结果迟到后再次查询，确认成功不被覆盖、历史仅两次且后置只消费一次。
4. 用户对照业务调用记录确认仅两次调用，流程成功完成，没有额外实例、等待重试或活动步骤。

### S10

1. 用户分别选择无重试配置及最多执行一次的两个流程，使用独立失败业务数据启动。
2. 用户通过公开运行查询分别核对单次尝试、失败原因，并对照各自业务调用记录。
3. 用户确认两者均没有再次调用或后置结果。
4. 用户确认两个流程均已失败，没有等待重试或活动步骤。

### S11

1. 用户分别保存最大次数为 0、负数及固定间隔为负数的独立草稿，并通过公开定义查询确认草稿内容。
2. 用户分别请求发布并观察明确拒绝。
3. 用户重新查询确认各草稿内容不变，没有新增正式版本、运行实例或业务调用。
4. 用户删除本场景草稿并查询确认已清理。

### S12

1. 用户选择包含失败重试分支和独立成功分支的并行流程并启动。
2. 用户通过公开运行查询确认重试分支仍在等待时，另一分支已完成且汇总尚未执行。
3. 用户查询重试成功后的业务记录与汇总结果，核对成功分支未重跑、失败操作调用两次、汇总消费两个结果一次。
4. 用户确认流程成功完成，没有等待重试或活动步骤。
