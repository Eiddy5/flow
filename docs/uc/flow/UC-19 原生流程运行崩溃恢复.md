# UC-19 原生流程运行崩溃恢复

## 验证标识

- UC：`UC-19`
- 状态：`ACCEPTED`
- 领域：`flow`
- UC 类型：`流程运行`
- 需求基线：`用户确认原生 Task 编排在各种情况下状态正确并能够崩溃恢复@2026-09-22`
- 依赖：`UC-02、UC-04、UC-05、UC-06、UC-09、UC-13、UC-14、UC-15、UC-16、UC-17、UC-18`

## 验证目标

用户通过原生 Task 编排流程，在服务突然退出、来不及完成正常关闭收尾后，仍可在服务
恢复时查询原运行并继续完成。已确认的步骤结果、选定路径、循环轮次、父子关联和
触发启动保持一致；未完成部分正确接续，已有终态不倒退，不因恢复而重跑已确认完成
的步骤、重复汇聚或增加运行实例。

## 验证场景

### S1 串行步骤之间崩溃后接续原运行

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小串行流程依次执行 A、B、C；B 消费 A 的确定输出，C 消费 B 的确定输出；本场景尚未启动
- 用户操作：用户启动并查询到 A 已完成、B 尚未完成且 C 未执行；服务此时突然退出，没有完成正常关闭收尾；运维用户恢复服务，发起用户按原编号查询，持续观察 B、C 和最终结果
- 预期结果：原运行编号、版本、输入及 A 的已确认输出保持不变，A 不重跑；B 可以继续完成，C 在 B 完成后消费正确结果且只完成一次；不要求重新启动流程，不跳过 B，不增加第二个运行实例
- 场景结束：原流程成功完成，没有活动或等待步骤

### S2 条件路径已选定后崩溃保持命中与跳过结果

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小流程按确定输入选择条件路径 A，另一条件路径 B 不命中；A 中有已完成步骤和未完成步骤，条件路径之后有后续步骤；本场景尚未启动
- 用户操作：用户启动并查询到 A 已命中、B 已跳过，记录 A 中已完成步骤的结果；在 A 尚未结束时服务突然退出且没有正常收尾；运维用户恢复服务，用户重新查询路径及后续结果
- 预期结果：恢复继续原实例的 A 路径，已确认结果不丢失且已完成步骤不重跑；B 保持已跳过，不产生 B 内步骤的执行或输出；A 完成后后续步骤仅消费 A 的结果一次
- 场景结束：原流程成功完成，没有额外实例或活动步骤

### S3 并行分支部分完成后崩溃只接续未完成分支

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小流程并行执行 A、B，随后汇总两者输出；A 能先于 B 完成；本场景尚未启动
- 用户操作：用户启动并查询到 A 已完成、B 尚未完成、汇总未执行；服务突然退出且没有正常收尾；运维用户恢复服务，用户按原编号重新查询两个分支及汇总结果
- 预期结果：A 的步骤编号和已确认输出保持不变且不重跑；B 正确继续，B 完成前不执行汇总；两个分支完成后汇总只执行一次并消费各自正确结果，不把恢复误当作新分支
- 场景结束：原流程成功完成，没有额外实例、活动分支或等待步骤

### S4 固定循环中途崩溃保留轮次与轮内进度

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小流程固定循环三轮，每轮串行执行 A、B，输出包含该轮可区分的值，循环后执行 C；本场景尚未启动
- 用户操作：用户启动，查询第一轮已完成、第二轮 A 已完成而 B 尚未完成；服务突然退出且没有正常收尾；运维用户恢复服务，用户重新查询当前轮、历史轮次及最终结果
- 预期结果：第一轮历史和第二轮 A 的结果保持不变且不重跑；从第二轮未完成部分继续，第二轮结束后才开始第三轮；各轮输入和输出不混用，不重复第二轮、不漏第三轮、不产生第四轮；C 在三轮完成后只执行一次
- 场景结束：原流程成功完成，保留完整三轮历史，没有活动轮次或等待步骤

### S5 条件循环崩溃后使用正确轮次结果判断结束

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小条件循环最多三轮，第一轮确定不满足结束条件，第二轮确定满足，循环后执行 C；本场景尚未启动
- 用户操作：用户启动并查询第一轮已完成且进入第二轮；第二轮尚未完成时服务突然退出且没有正常收尾；运维用户恢复服务，用户查询原实例的第二轮结果、停止原因和 C 的结果
- 预期结果：第一轮历史不丢失且不重跑，第二轮从原进度继续；第二轮完整结束后按第二轮结果结束循环，不误用第一轮结果，不产生第三轮；C 只执行一次并消费第二轮结果
- 场景结束：原流程成功完成，保留两轮历史，没有活动轮次或等待步骤

### S6 等待子流程期间崩溃保留原父子运行

- 参与用户：流程发起用户、流程处理用户和系统运维用户
- 开始状态：已发布最小父子流程，父流程传递确定输入调用子流程，子流程在一个 Pause 等待结果，父后续步骤消费子结果；本场景尚未启动
- 用户操作：发起用户启动父流程，查询并记录原父子编号、输入和子流程当前 Pause；服务突然退出且没有正常收尾；运维用户恢复服务，处理用户重新查询原子流程当前 Pause 并提交合法结果，再查询父子结果
- 预期结果：原父子运行编号、版本、来源关系和子输入保持不变，不另外创建子实例；重启本身不恢复 Pause，子流程仍等待合法结果，父后续步骤不提前执行；提交结果后子流程完成，父调用接收正确返回结果且后续步骤只执行一次
- 场景结束：原父子流程均成功完成，没有额外子实例、活动步骤或等待恢复的 Pause

### S7 子流程已结束但父调用未结束时崩溃后传回原结果

- 参与用户：流程发起用户和系统运维用户
- 开始状态：用户为子流程成功与子流程失败分别选择独立最小父子流程，父后续步骤仅在子调用成功时执行；本场景尚未启动
- 用户操作：用户分别启动父流程；每次在子流程已产生可查询终态而父调用尚未结束时，服务突然退出且没有正常收尾；运维用户恢复服务，用户重新查询原父子编号、子结果、父调用和父后续步骤
- 预期结果：两种情况下原子终态、结果和来源关系均保持不变，不重跑子流程或新增子实例；成功结果正确传回且父后续步骤消费一次，父流程成功完成；失败结果传回后父调用及父流程失败，原失败原因可追溯且父后续步骤不执行；父调用不永久等待
- 场景结束：成功组父子流程均成功完成，失败组父子流程均已失败，没有活动父子运行或等待步骤

### S8 等待重试时崩溃恢复原计划与尝试历史

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小串行流程中 A 首次失败、第二次成功，最多执行两次，固定间隔 10000 毫秒，B 消费 A 成功结果；本场景尚未启动
- 用户操作：用户启动并查询到首次失败、等待重试及下一次计划时间；到期前服务突然退出且没有正常收尾；运维用户恢复服务，用户按原编号查询原计划、后续实际尝试及最终结果
- 预期结果：原运行、步骤编号、首次失败记录及原计划时间不变；原计划到期前不提前调用，到期后能够继续第二次实际调用，不因重启重置尝试次数或延后为全新的等待周期；只有第二次成功结果供 B 消费一次，不多出第三次尝试
- 场景结束：原流程成功完成，没有额外实例、等待重试或活动步骤

### S9 定时启动已受理后崩溃不丢失或重复该次运行

- 参与用户：流程管理用户和系统运维用户
- 开始状态：用户分别准备独立的周期定时 Flow 和单个指定日期时间 Flow，均只有一个触发器且内容最小、结果确定；周期流程的下一次时间晚于本场景观察结束，日期流程仅有本次时间点
- 用户操作：用户查询配置和原有运行记录；分别在本次计划时间已到达、启动已被系统接纳但尚未运行完成时，服务突然退出且没有正常收尾；运维用户恢复服务，用户查询本次新增运行及结果，不手动补发启动
- 预期结果：每种定时条件本次均只产生一个运行实例并继续完成，不因重启丢失已受理启动，也不把同一次定时条件当作新启动；已存在的运行保持原编号、版本和已确认步骤结果，完成步骤不重跑；日期条件不会再产生第二个实例
- 场景结束：两个本次定时运行均成功完成，没有活动步骤；本场景的两个触发配置均已停用或删除，重新查询确认不会再启动实例

### S10 Webhook 启动已受理后崩溃继续本次运行

- 参与用户：具有目标 Flow 访问和启动权限的用户及系统运维用户
- 开始状态：已发布最小 Flow 配置一个 Webhook 触发器，用户具备合法身份和确定请求数据；本场景未发送请求且无其他启动来源
- 用户操作：用户查询配置及原有运行记录，通过公开 Webhook 入口发送一次合法请求并收到受理结果；本次运行尚未完成时服务突然退出且没有正常收尾；运维用户恢复服务，用户不重发请求而重新查询本次运行和最终结果
- 预期结果：已受理请求对应的运行能够完成，本次只新增一个实例；恢复不要求用户重发请求，不丢失请求输入或已确认结果，已完成步骤不重跑；若崩溃前已有运行编号，恢复后沿用该编号
- 场景结束：本次运行成功完成，没有额外实例、活动步骤或等待步骤

### S11 上游完成触发已受理后崩溃继续下游运行

- 参与用户：流程发起用户和系统运维用户
- 开始状态：已发布最小上游和下游流程，下游仅由该上游成功完成触发，双方无循环触发；本场景尚未启动上游
- 用户操作：用户查询配置与原有运行记录，启动一次上游；上游已成功完成且对应下游启动被系统接纳、下游尚未完成时，服务突然退出且没有正常收尾；运维用户恢复服务，用户重新查询上游与本次下游结果，不重新启动上游或下游
- 预期结果：上游保持原成功终态和输出且不重跑；已受理的下游启动不丢失，本次仅新增一个下游实例并正确继续完成；下游已存在时保持原编号和已确认结果，不因重新处理上游完成而增加实例或重跑已完成步骤
- 场景结束：原上游和本次下游均成功完成，没有额外实例、活动步骤或等待步骤

### S12 已完成、已失败和已取消的运行跨崩溃保持终态

- 参与用户：流程发起用户和系统运维用户
- 开始状态：用户准备三个独立最小 Flow，分别可以成功完成、明确失败、进入 Pause 后被取消；本场景尚未启动
- 用户操作：用户分别启动三个实例，查询第一个成功、第二个失败；查询第三个当前 Pause 后取消并重新查询确认取消；记录各自终态与结果后服务突然退出且没有正常收尾；运维用户恢复服务，用户多次重新查询原三个实例的状态、结果与步骤历史
- 预期结果：成功、失败、取消三个结果分别保持，已确认输出、失败原因和历史不丢失；无一实例重新运行、产生新步骤或被替换成新实例；失败和取消实例不会执行仅在成功时才能执行的后续步骤，取消的 Pause 不再次等待恢复
- 场景结束：三个原实例分别保持成功、失败和取消终态，没有新增实例、活动步骤或等待恢复的 Pause

## 验证方式

### S1

1. 用户选择串行 A、B、C 的已发布流程并启动，通过公开运行查询记录编号、版本、输入及 A 的完成结果，确认 B 未完成、C 未执行。
2. 服务突然退出且没有完成正常关闭收尾后，运维用户恢复服务；用户仅凭原运行编号重新查询。
3. 用户核对 A 的编号和结果未变且未再次执行，再查询 B 的完成结果以及 C 对 B 结果的唯一消费。
4. 用户查询确认原流程成功完成，无额外实例、活动或等待步骤。

### S2

1. 用户选择条件路径确定的流程并启动，通过公开查询确认 A 命中、B 跳过及 A 内已完成步骤的编号和结果。
2. 在 A 尚未结束时经历服务突然退出且未正常收尾，运维用户恢复服务后用户重新查询原实例。
3. 用户核对 A 的既有结果和剩余步骤，确认 B 保持跳过且 B 内步骤没有执行或输出，后续只消费 A 的结果一次。
4. 用户查询确认原流程成功完成，没有额外实例或活动步骤。

### S3

1. 用户启动并行 A、B 后汇总的流程，公开查询 A 已完成、B 未完成及汇总未执行，记录两分支编号和 A 输出。
2. 服务突然退出且未正常收尾，运维用户恢复服务后用户重新查询原运行和两个分支。
3. 用户核对 A 未重跑、B 接续及汇总没有提前执行，再查询汇总仅一次消费 A、B 正确输出。
4. 用户查询确认原流程成功完成，没有额外实例、活动分支或等待步骤。

### S4

1. 用户启动固定三轮的流程，通过公开运行查询确认第一轮完整结果、第二轮 A 已完成及 B 未完成，记录轮次与步骤编号。
2. 服务突然退出且未正常收尾后恢复，用户按原编号重新查询历史和当前轮次。
3. 用户核对原已完成步骤未重跑、轮次顺序正确、各轮结果独立，总计三轮且 C 只执行一次。
4. 用户查询确认原流程成功完成，保留三轮历史，没有活动轮次或等待步骤。

### S5

1. 用户启动最多三轮而第二轮满足结束条件的流程，公开查询第一轮结果和进入第二轮的原因。
2. 第二轮尚未完成时服务突然退出且未正常收尾，恢复后用户重新查询原运行的第二轮。
3. 用户核对第一轮未重跑、第二轮完整结果及停止原因，确认没有第三轮，C 仅消费第二轮结果一次。
4. 用户查询确认原流程成功完成，保留两轮历史，没有活动轮次或等待步骤。

### S6

1. 用户启动父流程，通过公开查询取得父子运行编号、输入、版本、来源关系以及子流程当前 Pause，确认父后续未执行。
2. 服务突然退出且未正常收尾后恢复，用户重新查询原父子运行，核对编号和关联不变且没有额外子实例。
3. 处理用户重新查询原子流程中当前等待的具体 Pause，向查询所得步骤提交合法结果，再查询子结果、父返回和后续的唯一消费结果。
4. 用户查询确认原父子流程均成功完成，没有额外子实例、活动步骤或等待恢复的 Pause。

### S7

1. 用户分别启动成功返回组和失败返回组的独立父子流程，通过公开查询确认原子流程已结束而父调用尚未结束，记录编号、结果或失败原因。
2. 每组分别经历服务突然退出且未正常收尾，再由运维用户恢复服务，用户查询各自原父子运行。
3. 用户核对无重复子实例或已完成步骤重跑；成功组的结果被父后续消费一次，失败组原因传回且父后续不执行。
4. 用户查询确认成功组父子均成功完成，失败组父子均已失败，没有活动父子运行或等待步骤。

### S8

1. 用户启动允许两次尝试的流程，公开查询并记录原运行、步骤、首次失败和下一次计划时间。
2. 计划到期前服务突然退出且未正常收尾，运维用户恢复服务后用户重新查询原计划及尝试历史。
3. 用户核对原计划时间不变且不提前调用，第二次实际调用成功，不出现第三次尝试，B 只消费成功结果一次。
4. 用户查询确认原流程成功完成，没有额外实例、等待重试或活动步骤。

### S9

1. 用户通过公开能力查询周期和指定日期流程各自的配置与原有运行，确认本次时间点和无其他启动来源。
2. 各自在计划时间到达且本次启动已受理、未运行完成时经历服务突然退出且未正常收尾，再由运维用户恢复服务；用户不手动补发启动。
3. 用户查询本次各自唯一新增实例，核对已有编号、版本、已确认结果和未完成部分的接续，确认没有同次重复启动或已完成步骤重跑。
4. 用户停用或删除本场景两个触发配置，查询确认本次两个实例均成功完成、没有活动步骤且不会再启动新实例。

### S10

1. 用户通过公开查询确认 Webhook 配置和原有运行，通过对应公开入口发送一次合法请求并记录受理结果。
2. 本次运行完成前服务突然退出且未正常收尾，运维用户恢复服务，用户不重发请求而查询目标流程的运行记录。
3. 用户识别本次唯一新增实例，核对输入、已有编号和结果保留，已完成步骤未重跑且未完成部分正确接续。
4. 用户查询确认该实例成功完成，没有额外实例、活动步骤或等待步骤。

### S11

1. 用户通过公开查询确认上游完成触发配置，只启动一次上游并查询其成功结果。
2. 对应下游启动已受理而未完成时服务突然退出且未正常收尾，运维用户恢复服务；用户不再次启动任一流程。
3. 用户查询上游原终态及唯一的本次下游运行，核对原编号、已确认结果和正确接续，确认无额外实例或已完成步骤重跑。
4. 用户查询确认上游与下游均成功完成，没有活动步骤或等待步骤。

### S12

1. 用户分别启动成功、失败和可取消的独立流程，通过公开查询确认前两个结果；查询第三个当前 Pause 后取消，再查询确认取消终态。
2. 用户记录三个原运行编号、终态、结果和历史；服务突然退出且未正常收尾后由运维用户恢复服务。
3. 用户多次公开查询原实例，核对各自终态及结果不变，没有新步骤、重跑、额外实例或错误后续结果。
4. 用户查询确认三个原实例分别保持成功、失败和取消，没有活动步骤或等待恢复的 Pause。
