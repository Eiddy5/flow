# UC-02 用户启动、查询与取消 Flow

## 验证标识

- UC：`UC-02`
- 状态：`ACCEPTED`
- 领域：`flow`
- UC 类型：`流程运行`
- 需求基线：`用户确认的 Flow 完整用户路径、Pause 与删除语义@2026-08-27`
- 依赖：`UC-01`

## 验证目标

验证用户只能启动当前可用的 Flow，运行中的 Flow 始终使用启动时选定的正式版本，
并且用户能够查询和取消准确的目标；Flow 进入 Pause 后，用户通过同一个 Flow 的
运行信息提交 Pause 结果并继续执行，多实例和系统重启不会混用运行数据。

## 验证场景

### S1 用户启动并完成当前版本

- 参与用户：Flow 发起用户和 Flow 处理用户
- 开始状态：版本 1 是当前可用版本，Flow 中包含一个 Pause 步骤
- 用户操作：发起用户启动并查询 Flow；处理用户查询该 Flow 当前的 Pause 步骤并提交结果；发起用户再查询最终结果
- 预期结果：只创建一个运行实例，该实例始终使用版本 1，Pause 结果提交后 Flow 继续执行并最终完成
- 场景结束：Flow 已完成，没有仍在等待恢复的 Pause 步骤

### S2 新版本发布前后的 Flow 分别完整运行

- 参与用户：旧 Flow 发起用户、新 Flow 发起用户和各自的 Flow 处理用户
- 开始状态：旧运行实例使用版本 1 并处于 Pause，随后版本 2 发布
- 用户操作：用户启动版本 2 对应的新实例；两组处理用户分别查询各自 Flow 的 Pause 步骤并提交结果；最后查询两个运行实例
- 预期结果：旧实例始终使用版本 1，新实例使用版本 2，两个实例的 Pause 结果和运行历史互不混用
- 场景结束：两个 Flow 运行实例都已完成且没有等待恢复的 Pause 步骤

### S3 用户取消准确的目标 Flow

- 参与用户：目标 Flow 发起用户、对照 Flow 发起用户和对照 Flow 处理用户
- 开始状态：目标实例和对照实例都处于 Pause
- 用户操作：用户查询并取消目标实例，再查询两个实例；对照 Flow 处理用户查询对照实例的 Pause 步骤并提交结果
- 预期结果：只有目标实例被取消，对照实例不受影响并继续完成
- 场景结束：目标 Flow 已取消，对照 Flow 已完成

### S4 用户启动不可用或不可见的 Flow

- 参与用户：普通用户和另一租户的用户
- 开始状态：目标 Flow 分别处于未发布、已删除、不存在或属于其他租户
- 用户操作：用户逐一请求启动，并在每次拒绝后查询自己的运行实例
- 预期结果：每次启动都被明确拒绝，不会错误启动其他版本或其他租户的 Flow
- 场景结束：没有创建任何 Flow 运行实例或 Pause 等待状态

### S5 用户取消不存在、越权或已经结束的 Flow

- 参与用户：普通用户、另一租户用户和合法对照 Flow 的处理用户
- 开始状态：目标分别不存在、属于其他租户、已经完成或已经取消
- 用户操作：用户逐一请求取消并重新查询；若存在合法对照实例，处理用户查询其 Pause 步骤并提交结果
- 预期结果：所有错误取消都被明确拒绝，目标和对照 Flow 的状态及历史不发生越权变化
- 场景结束：原终态保持不变，合法对照 Flow 已完成

### S6 Flow 处于 Pause 期间发布新版本

- 参与用户：旧 Flow 发起用户、新 Flow 发起用户和 Flow 处理用户
- 开始状态：旧运行实例使用版本 1 并处于 Pause
- 用户操作：用户发布版本 2；处理用户查询并恢复版本 1 的旧实例；随后用户启动并恢复版本 2 的新实例，再查询两个结果
- 预期结果：旧实例不会切换到版本 2，新实例使用版本 2，两条运行路径均按各自版本执行
- 场景结束：新旧两个 Flow 运行实例都已完成

### S7 恢复 Pause 与取消 Flow 发生竞争

- 参与用户：Flow 发起用户和 Flow 处理用户
- 开始状态：Flow 正处于一个已经被用户查询到的 Pause 步骤
- 用户操作：发起用户取消 Flow，同时处理用户向该 Pause 提交恢复结果；竞争结束后双方重新查询 Flow 和步骤历史
- 预期结果：恢复和取消最多只有一个生效，最终结果只能是已完成或已取消，不能出现相互矛盾的历史
- 场景结束：Flow 已完成或已取消，没有仍在等待恢复的 Pause 步骤

### S8 同一 Flow 的两个运行实例独立完成

- 参与用户：两个 Flow 发起用户
- 开始状态：同一个结果确定的简单 Flow 已经发布
- 用户操作：两个用户分别启动一次，并按各自取得的运行编号查询结果和完整步骤历史
- 预期结果：两个运行实例拥有不同编号和各自完整的输入、输出及步骤历史，任一实例的推进不会改变另一个实例
- 场景结束：两个 Flow 运行实例都已完成且没有活动步骤

### S9 系统重启后用户启动已发布 Flow

- 参与用户：Flow 发起用户
- 开始状态：一个结果确定的简单 Flow 已经发布，随后系统完成一次重启
- 用户操作：用户在重启后重新查询正式 Flow，启动并查询运行结果和完整步骤历史
- 预期结果：用户仍能启动重启前发布的版本，Flow 按原定义完整执行，没有跳步、重复或顺序变化
- 场景结束：Flow 已完成且没有活动步骤

## 验证方式

### S1

1. 用户发布版本 1 并启动 Flow。
2. 用户查询运行状态和当前 Pause 步骤，向查询所得 Pause 提交合法结果。
3. 用户重新查询 Flow 和步骤历史，确认只运行一个实例且始终使用版本 1。
4. 用户确认 Flow 已完成且没有等待恢复的 Pause 步骤。

### S2

1. 用户启动版本 1 的 Flow 并查询到 Pause 状态。
2. 用户发布版本 2 并启动第二个实例。
3. 用户分别查询两个实例的 Pause 步骤并提交结果，再查询两个实例的版本与历史。
4. 用户确认两个实例都已完成且相互隔离。

### S3

1. 用户启动目标 Flow 和对照 Flow，并查询到两个实例各自的 Pause 步骤。
2. 用户取消目标实例并重新查询目标状态。
3. 用户向对照实例的 Pause 提交结果。
4. 用户查询并确认目标已取消、对照已完成。

### S4

1. 用户准备未发布、已删除、不存在和其他租户的 Flow。
2. 用户分别请求启动这些 Flow。
3. 每次拒绝后，用户查询自己的运行实例。
4. 用户确认没有创建任何运行实例或 Pause 等待状态。

### S5

1. 用户准备不存在、越权、已完成和已取消的目标，并准备一个合法对照 Flow。
2. 用户分别发起取消请求并观察明确拒绝。
3. 用户重新查询所有目标，确认状态和历史没有变化。
4. 用户恢复合法对照 Flow，并查询确认对照 Flow 已完成。

### S6

1. 用户启动版本 1 的 Flow 并查询到 Pause 步骤。
2. 用户发布版本 2，再向版本 1 实例的 Pause 提交结果。
3. 用户启动版本 2 的实例，查询并恢复其 Pause。
4. 用户确认两个实例分别使用原版本且都已完成。

### S7

1. 用户启动 Flow 并查询、记录当前 Pause 步骤。
2. 发起用户取消 Flow，同时处理用户向该 Pause 提交恢复结果。
3. 双方重新查询 Flow 状态和步骤历史。
4. 用户确认只有一个结果生效，Flow 已完成或已取消且没有等待恢复的 Pause。

### S8

1. 用户发布一个结果确定的简单 Flow。
2. 两个用户分别启动一次，并保存各自得到的运行编号。
3. 两个用户分别按编号查询运行结果、输入、输出和步骤历史。
4. 用户确认两个实例拥有独立完整结果、都已完成且没有活动步骤。

### S9

1. 用户发布一个结果确定的简单 Flow，并等待系统完成重启。
2. 用户重新查询正式 Flow，确认原版本仍然可用后启动。
3. 用户查询运行结果、步骤顺序和每个步骤的执行次数。
4. 用户确认 Flow 按原定义完成，没有跳步、重复或活动步骤。
