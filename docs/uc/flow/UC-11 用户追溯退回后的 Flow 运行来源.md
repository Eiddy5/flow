# UC-11 用户追溯退回后的 Flow 运行来源

## 验证标识

- UC：`UC-11`
- 状态：`ACCEPTED`
- 领域：`flow`
- UC 类型：`流程运行`
- 需求基线：`退回新实例、直接父与整树最初实例及真实路径需求、主 Agent 采用的整体接替方案@2026-09-08`
- 依赖：`UC-02`、`UC-04`

## 验证目标

验证用户能够在连续退回后查询每个新运行实例的来源，用直接父运行编号和整条派生树
最初运行编号这两项区分“从哪个实例退回而来”和“最初从哪个实例开始”；能够沿这些
关系查询真实运行记录，还原退回前后的实际路径，区分沿用的有效结果与真正重新执行
的步骤，并查询最新实例完成、原实例停止后的完整历史。

## 验证场景

### S1 连续退回后追溯直接父实例、最初实例和真实路径

- 参与用户：Flow 发起用户和 Flow 处理用户
- 开始状态：用户已发布一个最小 Flow，依次包含准备步骤、可重新执行且结果可区分的目标步骤、一个 Pause 和消费目标步骤及 Pause 结果的后置步骤；本场景尚未启动运行实例
- 用户操作：用户启动并查询初始实例 E1，查询当前 Pause 和真实步骤历史，从 Pause 选择已经执行的目标步骤并填写原因退回；用户查询 E1 已停止，以及新实例 E2 的来源、沿用结果和重新执行记录，待其到达新的 Pause 后重新查询并选择当前有效的目标记录再次退回；用户查询 E2 已停止及新实例 E3 的来源，沿来源关系重新查询三个实例的真实历史，在 E3 的新 Pause 提交结果并查询后置结果，最后重新查询三个实例的来源关系和终态
- 预期结果：两次退回分别产生不同编号的 E2、E3，每次原实例停止，由新实例整体接替并从所选历史目标重新推进；每个派生实例的来源关系仅包含直接父运行编号和整树最初运行编号，E2 的直接父实例和最初实例均为 E1，E3 的直接父实例为 E2、最初实例为 E1；E1、E2、E3 真实发生的步骤、输入、已产生输出、状态变化及退回原因均可沿实例关系查询，退回前事实不被后来的重新执行覆盖；准备步骤的原运行编号及有效结果被继续使用，查询可识别为沿用记录，不会将其描述为 E2、E3 重新执行过；目标步骤各次重新执行产生新的运行编号及可区分结果，新实例后续产生的事实不会被写成原实例执行过；仅凭重新查询所得运行数据即可还原准备步骤、每次目标步骤及 Pause、两次退回和 E3 后置步骤的实际先后关系；后置步骤消费 E3 最新结果，尚未发生的步骤不会被补成已经执行的记录；实例结束后来源关系和真实历史仍可查询
- 场景结束：E3 已完成，E1、E2 均已停止，三个实例的来源关系及真实运行历史保留，没有等待恢复的 Pause

## 验证方式

### S1

1. 用户选择本场景的已发布最小 Flow 并启动，取得 E1 的运行编号；查询 E1 的准备结果、已执行目标步骤和当前 Pause。
2. 用户从查询所得 Pause 选择已执行目标步骤并填写原因退回，查询 E1 已停止及不同编号的新实例 E2，确认 E2 的直接父实例和最初实例均为 E1；查询 E2 沿用的准备结果和重新执行的目标步骤。
3. 用户在 E2 到达新的 Pause 后重新查询，选择 E2 当前有效的历史目标记录并填写第二个原因退回；查询 E2 已停止及不同编号的新实例 E3，确认 E3 的直接父实例为 E2、最初实例为 E1，来源关系只表达这两个运行编号。
4. 用户沿 E3、E2、E1 的来源关系重新查询真实运行数据，核对各次输入、已产生输出、状态变化、源 Pause、目标步骤和退回原因，确认准备步骤沿用原运行编号、重做目标使用新运行编号；没有把沿用结果标为新执行、没有覆盖旧事实，也没有补出尚未发生的步骤；根据这些数据还原真实执行和两次退回的先后路径。
5. 用户查询并恢复 E3 当前 Pause，再查询确认后置步骤消费 E3 最新结果且 E3 已完成；最后重新查询确认 E1、E2 保持停止、E3 后续事实没有被写成原实例执行过，来源关系和真实历史仍保留且没有等待恢复的 Pause。
