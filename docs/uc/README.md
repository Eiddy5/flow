# UC 用户场景

`docs/uc/` 保存用于验证当前代码框架是否满足业务要求的真实用户场景。UC 描述用户
如何开始、操作、查询和结束一个业务流程，不描述代码如何实现。

## 生成原则

- UC Agent 从已确认需求和生效架构中提炼场景并管理目录。
- `$generate-uc` 将单个场景契约整理为统一 Markdown。
- 需求和架构用于生成前内部审查，不写入最终 UC。
- 生产代码、测试代码和运行结果不能反向改变 UC 的预期。
- Test Agent 根据 UC 场景和验证方式检查当前代码框架。

## 目录结构

UC 按业务领域归档：

```text
docs/uc/
  README.md
  flow/
    README.md
    UC-01 Flow 草稿生命周期与多租户管理.md
    UC-02 用户启动、查询与取消 Flow.md
    UC-03 用户运行自动流程.md
    UC-04 用户处理外派任务并恢复流程.md
    UC-05 用户处理并行外派任务.md
    UC-06 用户提交外派结果后的条件路径.md
    UC-07 用户处理多阶段外派流程.md
```

新领域由 UC Agent 创建，同时建立领域 `README.md` 并说明边界、UC 清单、依赖和
推荐验证顺序。

`gaps/` 仅保留历史实现差距，不参与定义新 UC。

## UC 文档格式

每个新建或更新后的 UC 只允许四个二级章节：

1. `验证标识`
2. `验证目标`
3. `验证场景`
4. `验证方式`

每个场景必须包含：

- 参与用户。
- 开始状态。
- 用户操作。
- 预期结果。
- 场景结束。

每个场景都有同编号验证方式，使用真实用户操作形成独立闭环。异常场景同时描述
明确拒绝和无副作用结果。

UC 不保留规范来源、不变量、前置条件总表、PASS、规则追踪、待确认事项、变更
记录、能力缺口或反例章节，也不引用类、方法、Repository、数据库表、Mock、测试
类或代码路径。

## 变更规则

UC 只在用户确认需求或生效架构改变时调整。实现失败、测试失败或当前框架暂不支持
不是修改用户场景的理由。

未确认问题由 UC Agent 在交付说明中报告，不写入 `ACCEPTED` UC。

## 测试关系

```text
一个 UC Markdown
  -> 一个主测试类
  -> 场景 S*
  -> 场景中的预期结果与结束状态
  -> 测试断言和执行证据
  -> 场景结论
```

Test Agent 不得增加 UC 没有描述的业务预期，也不得为了让当前代码通过而放宽场景。

## 校验

```bash
python3 .codex/skills/generate-uc/scripts/validate_uc.py \
  --strict "docs/uc/<domain>/<UC-ID> <主题>.md"
```

当前 Flow UC 已全部迁移为四章节格式。后续新增或更新 UC 必须通过严格校验。
