# Repository Guidelines

## Project Structure & Module Organization

This is a Micronaut Java application built with Gradle Kotlin DSL. The authoritative
project directory map and directory responsibilities are documented in
`docs/project-structure.md`.

AI agents must read `docs/project-structure.md` before adding, moving, or reviewing
project files. Do not duplicate a second directory map in `AGENTS.md`; update that
document when the project structure changes.

## Build, Test, and Development Commands

Use the Gradle wrapper for all local commands:

```bash
./gradlew test
```

Runs the JUnit 5 and Micronaut test suite.

```bash
./gradlew run
```

Starts the Micronaut application locally.

```bash
./gradlew build
```

Compiles, tests, and assembles the project artifact.

```bash
./gradlew shadowJar
```

Builds a runnable shaded JAR when needed for deployment.

## Coding Style & Naming Conventions

Use Java 21. Keep packages under `org.cses.flow` unless the project package is intentionally changed. Use 4-space indentation, descriptive class names, and standard Java naming: `PascalCase` for classes, `camelCase` for methods and fields, and uppercase names for constants. Prefer constructor injection for Micronaut beans. Keep configuration keys lowercase and hierarchical in YAML.

## Testing Guidelines

Tests use JUnit 5 with Micronaut Test. Name test classes with the `*Test` suffix and place them under `src/test/java` in the matching package. For Micronaut integration tests, use `@MicronautTest`. Run `./gradlew test` before submitting changes. Add focused tests for new services, configuration behavior, and HTTP endpoints.

Before writing or running UC tests, or validating a completed UC, read and follow
`docs/standards/uc-testing.md` and `.codex/agents/test/README.md`.

## Project Codex Agents

Project-scoped Codex agents are configured under `.codex/agents/`:

- Delegate confirmed-requirement UC creation, updates, and coverage audits to the
  `uc` agent.
- Delegate UC test creation, execution, validation, and test-report generation to
  the `test` agent.

When one request needs both roles, run them sequentially: wait for `uc` to finish
the confirmed UC before starting `test`. The primary agent owns task scoping,
coordination, user questions, and the final consolidated response.

Each Agent uses a top-level `<name>.toml` as the Codex entry and a same-name
directory as its documentation package. Read the package `README.md`, then follow
its task-specific pointers. The detailed role boundaries are authoritative in
`.codex/agents/uc/README.md` and `.codex/agents/test/README.md`.

## Documentation Workspace

The `docs` directory is the project memory used by both humans and AI agents. Before making non-trivial changes, inspect the relevant files under `docs` and follow the documented project conventions. If a change creates a reusable rule, validation scenario, harness, or architecture decision, update the matching document or add a new Markdown file.

Current documentation structure:

```text
docs/
  project-structure.md # Authoritative project directory map and responsibilities
  uc/           # Pre-implementation descriptions of confirmed user scenarios
  test-reports/ # Bounded recent UC test execution reports
  standards/    # Development standards and project-specific implementation patterns
  harness/      # Reusable test/debug harnesses, local setup notes, scripts, and examples
  decisions/    # ADR records for important technical decisions
```

Use these directories as follows:

- `docs/uc/`: Store pre-implementation descriptions of user scenarios derived only from confirmed user requirements. UC documents describe user actions and observable results; they do not validate technical architecture. The authoritative creation, formatting, and validation rules are defined only by `.codex/skills/generate-uc/SKILL.md`. Execution evidence and counterexamples belong in `docs/test-reports/`.
- `docs/test-reports/`: Store the bounded set of recent UC test reports generated by Test Agent. Organize reports by UC domain and apply the rolling retention rule in `docs/standards/uc-testing.md` after every report run.
- `docs/standards/`: Store reusable development conventions and modeling methods that apply across multiple business objects or tasks. Do not place concrete Flow, Task, Execution, PAUSE, Data, State, module-shape, or runtime design choices here; those belong in `docs/decisions/`.
- `docs/harness/`: Store reusable execution and verification support, such as local environment setup, sample configs, command recipes, test data notes, generator runbooks, or curl examples.
- `docs/decisions/`: Store concrete domain, module, runtime, persistence, and architecture choices as decision records. Use numbered ADR names such as `0001-use-jooq-for-database-access.md`. Each ADR should include status, context, options considered, decision, rationale, and consequences. Use `docs/decisions/README.md` to locate the current Flow decision chain.

AI agents should use this workflow:

1. Read `docs/project-structure.md` to identify the target module, directory
   responsibility, public entry point, and dependency direction.
2. Read `docs/standards/development.md`; it is mandatory for every
   development and code review task.
3. Check `.codex/agents/` to identify any matching project Agent; read its package
   `README.md` and the task-specific documents it points to.
4. Read relevant files in `docs/standards/` before implementing project-specific code.
5. Check `docs/decisions/` before changing architecture, data access patterns, module boundaries, or build conventions.
6. Use `docs/uc/` to identify the confirmed user scenarios and verification paths for a change. Invoke `$generate-uc` when creating or updating a UC.
7. Add or update `docs/harness/` when a reusable local setup, script, sample, or debugging flow is discovered.
8. Add an ADR in `docs/decisions/` when the change makes or changes a significant technical decision.

## Commit & Pull Request Guidelines

This repository currently has no commit history, so use clear, imperative commit messages such as `Add flow controller` or `Fix Consul bootstrap config`. Keep each commit focused. Pull requests should include a short summary, testing performed, linked issue or task if available, and notes for configuration changes. Include screenshots only for user-visible UI changes.

## Security & Configuration Tips

Do not commit secrets, tokens, or environment-specific credentials. Prefer environment variables for deploy-time values such as `NODE_IP`. Treat `bootstrap.yaml` changes carefully because they affect configuration loading before the application starts.
