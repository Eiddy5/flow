# UC Agent 场景设计

创建、补充或审计 UC 场景时使用本文件。

## 需求基线

内部记录需求版本或确认日期，并提取：

- 参与用户。
- 开始状态。
- 用户操作。
- 用户能观察到的结果。
- 不得发生的副作用。
- 场景结束状态。
- 会改变用户场景结果的未确认需求。

这些分析用于保证场景正确，不直接写入 UC Markdown。

## UC 类型与归属

每个 UC 选择一个主要类型：

- `ORCHESTRATION`：流程定义、顺序、分支、并行、汇聚、嵌套及定义生命周期。
- `EXECUTION`：流程启动、推进、多实例、版本选择、取消、恢复及运行隔离。
- `TASK_TYPE`：一种具体 Task 在完整流程中的配置、执行结果和用户可观察行为。

类型按主要业务风险确定。一个场景只由一个 UC 负责；组合能力只有形成独立用户风险
时才建立场景。

用户要求“补齐 `<Task 类型>` task 的 UC”时，按 `TASK_TYPE` 增量审计；任务类型
名称明确时，直接采用该名称，不再要求用户重复指定类型或通用覆盖维度。例如补齐
Pause task 时，目标任务类型为 `PAUSE`。

## 场景扩展

先建立合法主流程，再检查适用维度：

- 不同用户、角色和租户。
- 不同合法状态和终止状态。
- 缺失、非法、边界和错误引用。
- 首次、重复、乱序和越权操作。
- 失败、重试、取消、恢复和竞争。
- 数量、顺序、关联和版本变化。
- 拒绝后的状态不变和资源清理。

只保留保护不同业务行为或风险的场景，不生成没有独立意义的输入组合。

## 增量补齐任务类型 UC

“补齐”表示保留有效内容并审计缺口：

1. 定位该 Task 类型已有 UC、领域索引和已确认需求。
2. 保留仍有效的场景，识别缺失场景和重复归属。
3. 使用 `$generate-uc` 的任务类型覆盖参考建立候选场景，让每个场景通过标准化最小
   流程验证一个主要结果。
4. 写入已确认规则能够唯一决定预期的场景。
5. 将超时、认领、转派、重试等会改变预期的未确认行为集中返回主 Agent；确认前不
   写入 `ACCEPTED` UC。
6. 将通用编排、版本、多实例和运行生命周期场景归入对应类型 UC；只有目标 Task
   自身行为变化时才保留交叉场景。

任务类型运行场景必须由用户定义并发布流程、启动独立流程实例、观察目标 Task 的
结果，再查询并推进到完成、失败或取消终态。

## 真实用户闭环

每个场景独立完成：

1. 用户准备、选择或查询业务对象。
2. 用户执行真实业务操作。
3. 用户重新查询结果。
4. 用户观察成功结果、拒绝结果和禁止副作用。
5. 用户将本场景创建的资源推进到终态或完成清理。

Flow 完成型运行场景不能停在 `CREATED`、`RUNNING` 或 `WAITING`，必须结束于完成、
失败或取消等终态。PAUSE 场景由被外派用户查询具体任务、完成查询所得任务、重新
查询后续任务，并最终查询到流程终态。

场景设计完成的判据是：每条已确认需求都有唯一场景归属，每个场景都能独立执行并
观察结束状态，所有会改变预期的未确认项均已隔离并返回主 Agent。
