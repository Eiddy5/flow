# Test Agent 测试设计

创建、补齐、同步或审计 UC 测试时使用本文件。

## 场景追踪

从目标 UC 提取 UC 类型、目标任务类型及验证流程、场景编号和名称、参与用户、开始
状态、用户操作、预期结果、场景结束和同编号验证方式，并建立完整关系：

```text
UC Markdown
  -> 唯一主测试类
  -> 场景 S*
  -> 测试方法
  -> 预期结果与场景结束断言
  -> 执行证据
  -> 场景结论
```

任一场景、预期结果或结束状态没有对应证据时，覆盖不完整。

## 测试组织

- 一个 UC 只对应一个主测试类，一个主测试类只对应一个 UC。
- 主测试类位于被测公开入口对应的 `src/test/java` 包中，类注释记录 UC 仓库相对
  路径。
- 每个 `S*` 对应一个可执行且未禁用的测试方法；方法名包含场景编号并表达业务
  行为。
- 一个场景的多个输入分支使用同一个参数化测试方法。
- `@Disabled`、空测试、TODO 和只调用不断言都不算覆盖。
- UC 范围过大时，将拆分需求返回 UC Agent，不通过拆分多个主测试类规避一一对应。

## 分类策略

### 流程编排

- 每个场景独立通过公开入口定义或修改并发布本场景流程。
- 断言顺序、分支、并行、汇聚、嵌套或定义生命周期等目标结构。
- 具体 Task 只作为结果确定的观察手段，不把 Task 自身行为混入编排断言。
- 不共享其他场景已经发布的流程。

### 流程运行

- 使用内容最小且结果确定的已发布流程。
- 验证启动、版本选择、多实例、推进、取消、恢复、竞争和运行隔离。
- 不重复验证流程结构是否合法或具体 Task 的特殊行为。

### 任务类型

- 读取 UC 的目标任务类型和每个场景的验证流程。
- 每个测试完整执行“定义标准流程—发布—启动—定位目标任务—触发结果—验证后续
  消费—查询终态”。
- 除 UC 明确要求多个目标任务外，标准流程只包含一个主要目标 Task。
- 通过完整流程验证目标 Task，不直接调用目标 Task 验证局部结果。
- 启动失败或被拒绝时，证明运行流程未创建且没有副作用。

## 创建与同步

- 写操作通过用户实际使用的公开 Service、Controller 或 HTTP 入口驱动；查询优先
  使用公开查询能力。
- 每条预期结果和场景结束事实至少对应一个明确断言。
- 拒绝场景同时断言错误结果、原有事实不变和资源收尾。
- 场景互相独立，不依赖方法顺序或其他场景遗留数据。
- 测试保持 UC 的完整步骤、查询和断言，不按当前实现降低预期。

同步已有测试时，先建立新增、匹配、失效和错误归属清单，再执行以下处理：

- 为新增场景创建方法，为变化场景重写对应方法和断言。
- 将不再属于该 UC 但仍有技术回归价值的测试迁移为语义明确的普通技术测试。
- 删除已经失效且没有独立技术价值的方法，清除错误的 UC 编号或场景映射。
- 保留仍然有效的失败证据和断言强度。

发现 UC 可能遗漏场景时，在结果和报告中列出，由 UC Agent 追溯需求。测试设计完成
的判据是：每个目标 UC 都能从场景逐项追踪到唯一测试方法及其全部断言，所有缺口均
已明确标记。
