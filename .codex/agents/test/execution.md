# Test Agent 执行与判定

运行测试、判定场景或复验反例时使用本文件。

## 验证环境

- Flow 核心 UC 默认使用真实 PostgreSQL 和真实 Micronaut 装配。
- 涉及系统重启时，关闭并重新创建 `ApplicationContext`，随后只使用用户可获得的
  业务标识和公开查询继续处理。
- 验收范围外的第三方系统可以使用替代实现；本次验证的流程、Execution、目标
  Task 和状态推进使用真实实现。
- 场景结束后检查仍在运行的流程和仍在等待的任务数量。

## 执行顺序

统一使用 Gradle Wrapper：

1. 编译目标模块。
2. 逐个运行目标 UC 主测试类。
3. 单独重跑首次失败的方法，确认结果是否稳定。
4. 运行目标模块测试。
5. 运行项目完整测试。
6. 涉及应用装配或 HTTP 时，执行对应启动和接口验证。

单个成功方法只能证明对应场景，不能替代目标 UC 或完整回归结论。

## 场景状态

每个场景只使用以下一种状态：

```text
PASS         已执行，全部预期结果和结束状态均有证据且符合 UC
FAIL         已执行，至少一个实际结果不符合 UC
NOT_COVERED  缺少测试、断言或其他充分证据
BLOCKED      因真实环境或验收范围外的外部依赖无法完成
```

测试类整体成功不使场景自动通过。任一预期结果或结束状态缺少证据时，该场景不是
`PASS`。

## 失败与反例

- 失败场景记录复现命令、用户输入、预期、实际结果和影响范围。
- 首次失败单独重跑；确认稳定的实现问题在报告中分配 `CE-*`。
- 覆盖缺失和环境问题分别使用 `NOT_COVERED`、`BLOCKED`，不记为反例。
- 反例复验保持原场景和原预期。
- UC 缺少明确预期、公开验证路径或场景结束状态时，将对应场景标记为
  `NOT_COVERED`，列出缺失信息并返回主 Agent。

执行完成的判据是：每个目标场景都有基于实际命令和观察结果的唯一状态，首次失败
已经复验，目标与回归执行结果以及活动资源数量均已记录。
