# 设计 PostgreSQL 表结构

按照“需求定界、领域建模、逻辑建模、物理设计、DDL、验证”的闭环开展工作。
从当前任务和项目资料中推导业务语义，不要沿用之前表设计任务中的表、字段、状态或
生命周期假设。

除非用户明确要求接入 Repository 或应用，否则只修改表结构及 SQL 相关产物。

6. 按以下优先级判断事实来源：用户最新明确决定、已确认的项目文档和 ADR、
   当前 Schema 基线、当前实现。发现冲突时，先说明冲突再修改 SQL。

## 明确需求

在确定数据表之前，明确以下信息：

- 领域边界、统一术语和业务职责。
- 一行数据代表的业务事实。
- 哪个 ID 是稳定业务身份，哪个 ID 标识具体存储记录。
- 租户边界和唯一性范围。
- 生命周期状态和合法状态转换。
- 版本、修订、历史记录和并发控制语义。
- 父子所有权及排序规则。
- 每个逻辑关系的基数和可选性。
- 内容是可查询的结构化数据，还是不可拆解的原始快照。
- 软删除和审计行为。
- 预期的读、写、队列、遍历和报表查询路径。
- 会影响设计的数据规模、保留周期及归档要求。

区分已确认需求、设计假设和未决事项。只有未决事项会实质影响数据身份、兼容性或
完整性时才要求用户决定；其他情况说明假设后继续。

## 从领域出发建模

根据领域含义推导表结构，不要直接照搬请求参数、页面、应用类或历史数据库：

- 确定本次设计所属的限界上下文或业务能力。
- 明确定义实体、值对象、事件、快照和参考数据，纠正模糊或一词多义的术语。
- 使用具体业务场景验证身份、所有权、可选性、基数、生命周期和版本行为。
- 将聚合边界视为一致性和事务边界的线索，不要机械地让一个聚合只对应一张表。
- 当领域概念具有持久身份、独立生命周期、独立查询价值或需要数据库约束时，
  为其建立独立表。
- 当一个值完全依附于拥有者、没有独立生命周期，也不需要独立查询或约束时，
  可以内嵌或序列化存储。
- 不要按应用类逐一生成数据表。
- 不要因为字段相似就合并语义不同的领域概念。
- 对照项目文档和代码核验已确认的术语与行为，在模型定稿前暴露冲突。

对于每个关系，同时记录两个方向的含义、基数、可选性、拥有者、创建和删除行为，
以及使该关系成立的业务不变量。

## 合理运用三范式

以第三范式作为默认建模起点：

- 满足第一范式：移除重复组，让需要查询的属性具有稳定且明确的标量含义。
- 满足第二范式：确保每个非主属性依赖完整候选键，尤其注意联合键场景。
- 满足第三范式：消除非主属性之间的传递依赖，让可以独立维护的事实拥有唯一归属。

不要机械地强制规范化。以下需求有明确依据时，可以使用 JSONB、数组、快照、
冗余字段、预计算值或合并表：

- 保存不解析的外部文档或不可变历史快照。
- 已测量或有充分证据表明联表成本影响关键读取路径。
- 保存预计算聚合或读模型。
- 属性结构灵活且没有稳定的关系模型。
- 领域明确接受有边界的最终一致性或冗余权衡。

每次偏离第三范式时，都要说明唯一事实来源、冗余内容、同步或重新计算机制、
失败后的修复方式，以及读、写和存储成本。不要把尚未理解的领域模型称为
“反范式设计”。

## 构建逻辑模型

- 让每张表只有一个明确的行含义和所有权边界。
- 区分稳定实体身份与不可变版本、修订、事件或快照。
- 对可以独立编辑或版本允许为空的对象赋予独立记录身份。
- 一对多关系在子表中保存拥有者的身份。
- 多对多关系具有独立唯一性、属性或生命周期时，使用关联表。
- 将经常查询或约束的属性放入有明确类型的字段。JSONB 只用于真正灵活或不拆解的
  内容，不要用它掩盖尚未定义的数据模型。
- 只有存在明确读取路径时才冗余数据，并说明如何保持一致。

不要把可空字段作为主键的一部分。不要把并发修订号当作业务身份。

## 生成表关系图

逻辑模型稳定后、编写 SQL 前，必须生成简洁的 Mermaid `erDiagram`：

- 展示当前范围内的所有表，以及重要的主键、候选键和关系字段。
- 展示关系方向、基数和可选性。
- 即使物理数据库不创建外键，也要展示逻辑关系。
- 在配套说明中区分逻辑关系与数据库实际强制的外键。
- 保持图表可读；不会影响关系理解的载荷字段可以省略。
- SQL 定稿后再次更新关系图，确保表名、键和关系与最终 SQL 一致。

说明会影响后续演进的数据身份、版本、所有权和规范化选择。

## 设计物理约束

以下内容是跨项目的约束选择方法；项目规范可以进一步限制数据库承担的校验职责。
当前 Flow 项目以 `docs/standards/postgresql-schema.md` 为准，不使用 `CHECK`、外键或
其他数据库业务校验对象。

明确决定每个不变量由哪里保证：

- 使用 `PRIMARY KEY` 标识一行数据。
- 使用 `UNIQUE` 约束或唯一索引保证候选键和幂等键。
- 使用 `NOT NULL` 和 `CHECK` 约束保证单行数据不变量。
- 当唯一性依赖状态或软删除条件时，使用部分唯一索引。
- 项目禁用外键时，使用应用校验和事务写入保证跨表不变量。
- 乐观锁字段只用于并发冲突检测，不用于表达业务身份。

根据已经确认的访问路径设计索引：

- 查询总是包含租户或分区条件时，将该条件放在联合索引前部。
- 根据实际需要支持业务键查询、状态队列、父子遍历、版本获取和时间顺序查询。
- 活跃数据只占较小部分时，优先考虑部分索引。
- 避免创建已经被主键或唯一索引覆盖的重复索引。
- 为低选择性字段建索引前，评估写放大和维护成本。

明确软删除规则，包括已删除数据是否继续参与唯一性，以及子记录能否保持有效。

## 有依据地使用 PostgreSQL 特性

当 PostgreSQL 原生能力能够比应用约定更准确地表达数据语义、不变量或查询路径时，
优先考虑使用：

- 只有语义与领域匹配时，才使用 `jsonb`、数组、网络、范围和多范围等原生类型。
- 对有明确文档查询需求的 JSONB 使用相应操作符和 GIN 索引；把稳定且频繁过滤的值
  提取为有类型字段或生成列。
- 对需要直接过滤、索引或保证唯一性的确定性派生值使用生成列。
- 针对具体查询形态使用部分索引、表达式索引和覆盖索引（`INCLUDE`）。
- 使用排他约束和范围类型表达预约、有效期等不可重叠规则。
- 只有数据量、保留策略、分区裁剪或维护需求足以抵消运维成本时，才使用声明式分区。
- 只有确认需要数据库强制执行租户或访问隔离时，才使用行级安全策略。
- 使用 `citext` 等扩展前，先确认部署环境支持方式和迁移归属。

选择特性时评估可移植性、运维复杂度、写入成本、在线迁移行为和团队维护能力。
不要仅仅因为 PostgreSQL 提供某项特性就使用它。

## 应用项目 SQL 规范

以下规则是当前项目默认规范。在其他项目使用本 Skill 时，要重新读取项目文档和
用户明确决定，不要假设这些规则仍然成立：

- 使用 PostgreSQL 语法。
- 使用由应用生成的 `varchar(64)` 技术 ID。
- 需要审计快照时，使用 `creator`、`updater` 和 `deleter` JSONB 字段保存用户快照；
  只有需要直接过滤或索引时才增加派生的操作者 ID 字段。
- PostgreSQL 的所有时间点使用 UTC Unix timestamp 毫秒 `bigint`，字段名使用
  `*_at`；时长、超时和间隔使用带单位的 `*_millis` 等字段并同样保存为 `bigint`。
- 项目自有时间语义不使用 PostgreSQL `date`、`time`、`timestamp`、`timestamptz`
  或 `interval`。领域审计时间由领域产生，数据库只可为自身拥有的纯技术时间提供
  `bigint` 默认值。
- 需要软删除时使用 `deleted_at`。
- 无法避免使用 SQL 关键字作为字段名时加双引号，例如 `"order"`。
- 不生成 PostgreSQL 外键、`CHECK`、排他约束、Trigger、Rule、存储
  Function/Procedure、自定义 Domain 或 Enum 等数据库业务校验对象。通过关系字段、
  应用校验、主键、唯一约束、非空和查询索引表达存储与访问边界。
- 根据实际查询路径增加租户查询、状态队列、父子遍历、有序读取和历史查询索引。
- JSON 类型、状态、版本、软删除和关系一致性由应用对应所有权边界校验。
- 表结构文件隔离与表命名遵循 `docs/standards/postgresql-schema.md`；字段、索引和
  约束继续使用小写蛇形命名。

## 维护开发期基线 SQL

当前项目处于允许丢弃旧数据的开发阶段，完整 Schema 由一个入口和按表隔离的脚本
共同维护：

```text
gen/sql/flow/001_create_flow_tables.sql
gen/sql/flow/tables/<table_name>.sql
```

修改表、字段、索引和约束时只编辑该表的同名脚本。新增表时新增同名脚本，并在完整
入口中显式加入一次；入口只编排表脚本，不直接定义表。不要新增日期目录、增量
ALTER 脚本、回填脚本或旧模型兼容分支。基线变化后显式重建开发数据库并重新生成
JOOQ；不要在应用启动时自动删表或清库。

每个表脚本使用 `CREATE TABLE IF NOT EXISTS`，所属索引使用
`CREATE [UNIQUE] INDEX IF NOT EXISTS`；约束与表定义放在同一条建表语句中。完整入口
使用 `BEGIN` / `COMMIT` 保证一次建表的原子性。具体文件与命名完成条件只由
`docs/standards/postgresql-schema.md` 定义。

`IF NOT EXISTS` 只能保证相同基线重复执行安全，不能修正名称相同但定义不同的已有
对象。修改后的基线只支持空数据库；旧数据库和旧数据不在开发期兼容范围。进入需要
保留生产数据的发布阶段前，必须先通过新 ADR 冻结基线并重新定义追加迁移规则。

## 验证

执行当前项目规范要求的静态检查：

```bash
rg -n "FOREIGN KEY|REFERENCES|CONSTRAINT fk_" gen/sql/flow/tables
rg -n "CHECK\s*\(|CREATE\s+(TRIGGER|RULE|FUNCTION|PROCEDURE|DOMAIN|TYPE)" \
  gen/sql/flow/tables
rg -n "\b(date|time|timetz|timestamp|timestamptz|interval)\b" \
  gen/sql/flow/tables
```

按照当前项目规则，以上检查都不应匹配任何内容。

使用 PostgreSQL 验证完整基线：

```bash
.codex/skills/design-postgres-schema/scripts/validate_postgres_schema.sh \
  gen/sql/flow/001_create_flow_tables.sql
```

验证脚本必须：

- 确认每个表文件只定义一张同名表，入口恰好包含全部表文件；
- 确认所有表名是小写蛇形，且最后一个单词按项目规则使用复数；
- 成功执行完整基线；
- 再次成功执行同一基线；
- 确认最终数据库表集合与表文件集合一致；
- 确认 PostgreSQL 外键数量为零；
- 确认 PostgreSQL `CHECK`、排他约束、用户 Trigger、Rule、存储 Function/Procedure、
  自定义 Domain 和 Enum 数量均为零；
- 确认所有 `*_at` 和 `*_millis` 字段都是 `bigint`，并且不存在 PostgreSQL 原生
  日期时间字段；
- 删除临时数据库容器。

不验证旧 Schema 的升级路径；每次变更都验证空库建表、相同基线重复执行以及最终
Schema 与 JOOQ/Repository 契约一致。
