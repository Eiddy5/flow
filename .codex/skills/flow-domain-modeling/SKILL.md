# Flow Domain Modeling

把业务讨论整理成可审查、可实现的目标领域模型。始终从业务事实和不变量出发，
不要让现有 Java 类、数据库表或接口 DTO 反向决定领域。

## 必读资料

开始任何建模动作前，完整读取：

1. `../../../docs/project-structure.md`
2. `../../../docs/standards/development-basics.md`
3. `../../../docs/standards/domain-object-modeling.md`
4. `../../../CONTEXT.md`

然后只读取当前领域相关的：

- `docs/standards/*-domain-model.md` 与相邻领域规范。
- `docs/decisions/` 中涉及聚合、生命周期、版本或持久化边界的 ADR。
- `docs/uc/` 中对应的正向、反向和变异场景。
- `server/src/main/java/.../core/domains`、Repository、Handler、Service 和测试。

使用 `rg` 定位术语、字段、方法和状态。把代码视为实现证据，不把它视为当然正确
的模型。

## 固定建模流程

### 1. 明确范围和证据

先说明本轮只设计哪个领域以及相邻对象为何需要被读取。建立以下证据优先级：

1. 本轮已经确认的业务语义。
2. `CONTEXT.md` 中的统一语言和有效 ADR。
3. 已确认的领域标准与 UC。
4. 现有代码和数据库实现。

发现冲突时立即指出具体冲突和影响，使用业务场景确认目标语义。不要静默折中，
也不要创建兼容对象让两套模型长期并存。

### 2. 固化统一语言

对每个候选对象回答：

- 它是什么？
- 它明确不是什么？
- 哪些同义名称不再使用？
- 哪个业务事实要求它独立存在？

术语确认后立即更新 `CONTEXT.md`，使用一到两句定义和 `_Avoid_` 名称。只写业务
语言，不写 Java、数据库或接口实现。

### 3. 确认对象角色和聚合边界

把对象明确分类为聚合根、聚合内实体、值对象、状态枚举、领域服务或边界能力。
逐项确认：

- 哪些不变量必须在一次事务中成立？
- 谁可以创建和改变内部对象？
- 内部对象能否脱离根对象存在？
- 其他聚合只需要稳定 ID，还是确实需要完整对象？
- 谁拥有 Repository？

只有聚合根拥有独立 Repository。聚合内实体只能经聚合根创建和改变。聚合之间
使用稳定 ID 引用；跨聚合加载、事务和保存交给 Handler 或领域服务编排。

当两个对象的有效性条件、生命周期或失败语义不同，把它们拆成不同对象。原始或
尚未校验的来源不能继承始终有效的目标对象；只有子类型始终满足父类型全部不变量
时才允许继承。

### 4. 先设计生命周期，再设计字段和方法

先列出唯一初始状态、允许状态、终态和全部合法转换。对每个动作写清：

- 前置状态和输入。
- 原子改变的字段。
- 是否产生业务版本。
- 失败时必须保持不变的事实。
- 非法转换的领域错误。

如果某个状态要求大量核心字段为空，优先拆分对象，而不是用 `null` 和状态兼容
两种不同有效性。

### 5. 选择最小业务字段

逐项分类身份、业务、关系、生命周期、审计、并发和派生字段，并记录每个字段的
业务含义与约束。

- 只保存对象拥有且不能稳定推导的事实。
- 区分技术 `id`、业务标识、业务 `reversion` 和并发 `lockVersion`。
- 可空字段必须有明确业务含义。
- 集合保持顺序时说明顺序代表什么，并要求防御性复制和只读访问。
- 不把 Command、DTO、数据库 Record、解析中间对象或任意 Snapshot 塞入领域。
- 没有得到业务确认的字段放入“待确认”，不要自行补齐。

### 6. 设计业务方法

让方法围绕完整业务动作保护不变量：

- 只保留一个普通 `create`，并始终创建同一种合法初始形态。
- 把版本计算、状态变更和同一动作的业务副作用收进真正的业务方法。
- 不拆出 `createUpgradeDraft` 之类只服务编排的便利方法；升级属于部署时，就由
  `deploy` 原子完成。
- 使用 `start`、`complete`、`fail`、`cancel`、`close` 等业务动词。
- 不暴露 `setStatus`、`setReversion`、`setOutputs` 等公共 Setter。
- 子实体变更方法限制可见性，只允许聚合根调用。
- 使用 `rehydrate` 表达可信 Repository 重建；它不生成 ID 或触发业务转换。
- 查询方法表达集合真实语义；并行集合不要压缩成单数 `currentXxx()`。

方法归属遵守：

| 逻辑 | 归属 |
| --- | --- |
| 只依赖一个聚合并维护其不变量 | 聚合根或所属领域对象 |
| 修改聚合内实体 | 聚合根公开方法，实体内部方法 |
| 跨聚合纯业务规则 | 领域服务 |
| 加载、事务和保存 | Handler、Repository |
| 解析、序列化和第三方调用 | 边界 Service 或 Adapter |
| API 参数和响应转换 | Core 外部 Adapter |

### 7. 画类图并编号不变量

使用 Mermaid `classDiagram` 展示：

- 对象角色、全部目标字段和方法名。
- 继承、实现、组合、聚合和跨聚合 ID 引用。
- 一对一、一对多和可空关系。
- 枚举的完整状态。
- 静态创建/重建方法和受限可见方法。

不要把类图画成数据库 ER 图。类图后用表格解释每个字段和方法，不让图承担全部
语义。

为每个聚合和实体编写稳定编号的不变量，例如 `EXEC-001`、`RUN-001`。确保每条
可变不变量都有唯一负责的领域方法或聚合入口。

### 8. 用场景反证模型

至少覆盖：

- 正向：每条合法状态转换。
- 反向：非法状态、跨租户、错误引用和缺少必填事实。
- 变异：删掉关键校验、错误递增版本或绕过聚合后测试必须失败。
- 身份：创建、保存、重建和状态变化后 ID 稳定。
- 版本：成功版本动作递增，失败和非版本动作不递增。
- 恢复：重建后顺序、关系和下一步推导不变。
- 并发：重复命令或旧 `lockVersion` 不重复产生事实。

存在未确认策略时，把它单独列为“尚待业务规则确认”，说明它阻塞哪些实现或 UC。
不要猜测默认策略。

### 9. 落地并同步项目记忆

写文档前完整读取 [领域模型文档模板](references/domain-model-document-template.md)，
并在
`docs/standards/` 创建或更新唯一目标规范。文档必须同时表达目标模型和现有实现
迁移差距，不能把旧代码写成目标设计。

同一轮同步：

- `CONTEXT.md` 的术语。
- 相邻领域规范的引用和边界。
- 受影响的 UC、旧标准和旧设计文档。
- 代码、字段和方法仍未迁移的差距清单。

只有同时满足“难以逆转、脱离上下文会令人意外、存在真实取舍”时才新增 ADR。
新增前读取现有 ADR 格式，并遵循本仓库 `docs/decisions/` 的编号和结构要求。

## 交付要求

每个领域至少交付：

- 一句话定义和不使用的名称。
- 对象角色、聚合边界和 Repository 边界。
- 包含字段和方法名的 Mermaid 类图。
- 字段规则、业务方法和状态转换。
- 业务版本、审计与并发版本的区分。
- 编号不变量。
- 正向、反向、变异、恢复和并发场景。
- 待确认规则。
- 目标模型与现有实现的迁移差距。
- 受影响文档的同步结果。

先把文档交给用户审查；只有用户明确要求实现时才修改 Java、数据库或运行链路。

## 校验

对本轮领域文档运行：

```bash
python3 .codex/skills/flow-domain-modeling/scripts/validate_domain_docs.py \
  --strict docs/standards/<domain>-domain-model.md
```

再对本轮实际修改的文件运行定向 `git diff --check -- <files...>`。如果全仓库存在
无关的存量错误，只报告它们，不要顺手修改。

Skill 自身发生变化时，额外运行：

```bash
uv run --with pyyaml python \
  "${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-creator/scripts/quick_validate.py" \
  .codex/skills/flow-domain-modeling
```

## 禁止事项

- 不从表字段或现有 Getter 列表直接生成领域模型。
- 不以“以后可能需要”为理由增加状态、字段、继承层次或 Repository。
- 不把应用编排方法伪装成领域方法。
- 不用公共 Setter、可变集合或可空字段绕过不变量。
- 不用 `version` 混称业务 `reversion` 和技术 `lockVersion`。
- 不在 `CONTEXT.md` 写实现细节。
- 不把尚待确认的行为写成既定规则。
- 不只新增新规范而保留冲突旧文档不处理。
